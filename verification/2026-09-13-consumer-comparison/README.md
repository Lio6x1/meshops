# Entity 单实例与三实例消费对照

2026-09-13，本机 Windows / Docker Desktop；基线提交 `0f9589a5a80e98f40ba6ee4a3a0450511918c1fb`。

结论：本次固定总资源的小样本对照中，三实例完成吞吐均值比单实例高约 9.4%，但四轮都未通过 2,000 events/s 验收。三实例有一轮生成队列丢弃，不能当作无损能力提升。增加进程可以缓解部分争用，尚不能解决当前链路瓶颈，更不能据此宣称百万实体高频上报已达标。

## 条件与口径

- 10,000 个混合类型实体、10 个模拟来源，使用现有六类实体生成器；每轮全量预热并验证 10,000 个快照，再按 2,000 events/s 生成 30 秒，共计划 60,000 条，单条上报。
- Kafka topic 固定 3 分区。Entity 同时启动状态投影组和历史消费组；每组每分区一个串行 worker。因此单实例本来就能并行处理 3 个分区；三实例是把这 3 个分区分配给 3 个进程，并没有变成 9 个分区。
- 每轮在供压前通过 DescribeGroups 验证两个组都 Stable、成员数准确、分区 0/1/2 各分配一次；见各轮 `assignments.json`。
- 压测器、Ingest、全部 Entity 共享 runner 的 **4 CPU / 3 GiB**；MySQL 2 CPU / 1 GiB，Kafka 2 CPU / 1.5 GiB，Redis 2 CPU / 1.5 GiB（maxmemory 1 GiB）。增加进程没有增加总硬件配额。
- 每轮使用独立实验 Compose 项目及全新数据卷，沿用现有持久化配置。用户演示服务始终保持运行，构成共同背景负载；未同时跑其他本次实验轮次。
- 历史仍只采样 100 个符合条件的实体，并保留原有每实例预算。有效轮次实际均写入 600 条本阶段历史记录，加预热 100 条共 700 条；未观察到预算跳过。不能把本次视为所有上报均写 MySQL 的测试。
- “完成吞吐”是 accepted / elapsedIncludingDrainSeconds，包含生成、工作队列处理、观测等待与有限排空，并非纯消费循环速率。可见延迟是抽样的“计划生成到可查询状态”时间，包含生成器排队等开销，不等于纯 Kafka 延迟。
- 原始验收未放宽：无丢弃、无错误、无观测缺失，最终两组 lag=0，生成及完成吞吐至少达到目标的 95%。

四轮 publish errors 和 observation misses 均为 0。三实例均值约 1,666.3，单实例约 1,523.1，均值比约 +9.4%；仅两次重复，顺序也未完全平衡，不提供统计显著性或通用扩容收益保证。第 3 轮丢弃发生在压测生成队列，不能描述成 Kafka 接收后丢失。

第 1 轮未产生有效负载，错误为 `database_create: MySQL unavailable`，不计入性能统计。排查发现原健康检查使用 localhost socket，可能在 MySQL 初始化临时服务阶段提前就绪；实验副本随后改为 `127.0.0.1` TCP 探测。第 2 轮启动时仍使用旧检查，第 3—5 轮使用新检查。原计划顺序为 1/3/3/1，补测第 5 轮单实例后，有效实际顺序是 3/3/1/1；各 summary 的 `order` 字段保留原计划，不代表五轮实际顺序。

所有有效轮次都在 2,000 档失败，因此预设的 **5,000 档未执行**。本次也**没有重跑百万实体**、订阅扇出、任务下发或多机扩容。

## 从测量中能看出的限制

1. **逐条同步提交位点值得优先优化验证。** 两个消费组的 commit 在实测 handler+commit 累计墙钟时间中占约 57%—66%。这不是 CPU 百分比，也未覆盖 fetch 等其他时间；但足以说明提交成本不可忽略。后续可对连续成功位点做有界批量提交，必须同时验证崩溃重放和幂等性，不能直接跳过提交。
2. **历史锁等待确有缓解。** 单实例本阶段 600 次候选处理的累计锁等待约 22.2—24.4 秒，三实例约 0.002 秒；累计持锁时间仍约 21—31 秒。分区分到不同进程后减少了本地锁争用，数据库操作成本仍在。这些是多次调用累加时间，不是请求 P99 或整轮耗时。
3. **共享 CPU 也构成限制迹象。** 全轮资源采样中，Kafka CPU 峰值约 204%—215%（配额 2 CPU）；三实例 runner 峰值约 416%—422%（配额 4 CPU）。短时 Docker 采样可略超过配额，不能当作持续使用量；本次未采集 cgroup throttling，不能直接下节流定论。多进程会与同容器压测器和 Ingest 争用资源，不能从此次结果证明“只需再加机器”或“全是代码问题”。
4. **本次不是正式多实例上线验收。** 只比较共享 Redis 状态投影与历史处理，未覆盖跨实例订阅、成员故障重平衡、网络分区等完整运行边界。

建议下一步保持相同正确性验收，分别测试位点批量提交和历史锁粒度改进；再将压测器与服务资源分离做容量对照。一次只改变一个关键因素。

## 证据和实验改动

- `analysis.json`：由各轮阶段前后 Prometheus 计数差计算的 handler/commit、锁耗时和历史记录数。
- 各轮目录：脱敏 `summary.json`、`benchmark.json`、`assignments.json`，以及原样资源、周期诊断和阶段诊断 JSONL。
- `manifest.json`：每份证据原始/归档 SHA-256、长度及脱敏方式。没有归档运行凭证、生成配置、数据库连接串或临时二进制。
- `reproduce/`：本次实验构造、运行及分析脚本。生产 Go 源码未修改；临时副本只增加副本启动、分区分配断言、诊断采集及 Summary 耗时测量，没有改消费处理/提交逻辑。构建阶段执行了 verification/bus 单元测试并通过。

临时 Summary 不计算分位数，但插桩仍有成本。两组使用同一实验镜像；结果用于本次相对比较，不和以前未插桩、背景不同的验收绝对值直接对比。

## Windows 复现

先在基线提交的独立目录中准备 Go、Python、Docker Desktop，在仓库根目录运行。脚本固定只管理 `meshops-consumer-compare` 项目，因此不要同时启动两份对照实验。

```powershell
New-Item -ItemType Directory -Force .cache/consumer-compare | Out-Null
Copy-Item verification/2026-09-13-consumer-comparison/reproduce/*.py .cache/consumer-compare/
python .cache/consumer-compare/prepare.py
docker build --target backend -t meshops-consumer-compare:experiment .cache/consumer-compare/source
python .cache/consumer-compare/run.py
python .cache/consumer-compare/analyze.py
```

构建失败时先解决构建问题，不要继续运行旧镜像。脚本运行过程中性能不达标会写 `outcome: failed`，Python 驱动脚本正常结束不等于验收通过。每轮结果位于 `.cache/consumer-compare/source/.local/scale/runs/`。`run-extra.py` 是本次替代无效第一轮的补测脚本；正常四轮全部有效时不必额外运行。归档的 prepare 使用最终 TCP 就绪检查，因此不会刻意复现首轮初始化失败。

仅重算已归档数据时，可将每轮目录按其原始布局恢复到分析脚本期望的位置，或直接阅读 `analysis.json`；分析脚本并不把缺失诊断当作通过。
