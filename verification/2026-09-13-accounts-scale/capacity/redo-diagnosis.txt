方法与清理

使用随机 binding_diag_<UUID> 数据库，表结构为 binding_key 主键及 binding_json JSON。
每组执行 START TRANSACTION、INSERT、服务器计时查询、ROLLBACK；最后 DROP 该诊断库成功。
服务器计时不含 rollback，端到端计时包含 docker exec、SQL 传输和 rollback；两者都不含 Python 构造 JSON/SQL 的耗时。
没有重放百万实体此前的持续写入压力；未改变业务代码、配置、资源限制或数据库超时。

结论与边界
原百万初始化期间，从 06:02:19Z 至 06:03:26Z 持续出现 MY-014084 redo 空间无法回收、log_checkpointer 落后的警告。
100 MiB redo 容量及这些警告，比“来源 JSON 单批太大”提供了更直接的瓶颈证据。
31.8 MB 来源合批独立插入成功且小于 64 MiB 包上限；但不能由此断言其在原持续写入压力下没有成本。
建议由 parent 在独立压测环境调整 redo 容量后按原参数复测，保留事务原子性、完整校验、RAM/CPU 和超时边界。
本诊断未验证百万实体持续运行能力，也未证明调整后百万初始化会通过。
