# 实体基数与事件速率：前七次容量运行

本页按现有七份 `summary.json`、资源采样和诊断记录整理。已证实的是：**一万实体下 500、2000 事件/秒的单个阶段通过；5000 阶段失败；十万实体下 500 阶段通过，但预热快照不满足全部实时新鲜；百万实体前三次都在初始化失败。** 按 4 MiB 软字节预算拆分 INSERT 后的新环境百万复测正在运行，结果留在[第8次补录区](#run-08)，当前不写通过。

## 口径与环境

“实体数”是不同实体 ID 的总数；“事件/秒”是这些实体合计的目标更新频率。它们也不同于连接数、订阅数。百万实体加 500 事件/秒的参数，不表示百万事件/秒；实际未完成初始化的运行更不能算作百万实体容量已验证。

运行范围是经过鉴权的 `Ingest → Kafka → Entity → Redis/MySQL`，不包含 gateway bbolt、任务链路和订阅扇出。mixed 场景使用十个来源、六类实体，person/drone/vehicle/robot 各占 20%，sensor/facility 各占 10%；Kafka 三分区，报告中的 Batch 为 1。预热逐个验证全部保留快照的身份、来源、类型、代次和版本；持续阶段的观测延迟采用轮换抽样，不能混称为全部实体逐条延迟统计。

七次运行的资源上限来自各自 summary：runner 4 CPU / 3 GiB，MySQL 2 CPU / 1 GiB，Kafka 2 CPU / 1.5 GiB，Redis 2 CPU / 1.5 GiB 且 `maxmemory=1 GiB`。每档目标负载持续 30 秒，资源采样周期 5 秒；一万实体总时限 900 秒、预热上限 600 秒，十万/百万分别为 1800 秒和 1200 秒。它们是本轮有界短时实验，不是长时间稳定性保证。

`generatedEventsPerSecond` 判断是否真正供上目标速率；`acceptedEventsPerSecond` 的时间分母含排空等待。丢弃、少发、接收不完整或未排空均不能因 RPC `errors=0` 而通过。`projectorLag/historyLag` 是阶段排空后的积压，不代表整个阶段从未积压。

## 一万实体：阶段通过不等于整个阶梯通过

第3次的预热接收及核验均为 10,000，过期数为 0。三档负载结果如下，均来自同一份 summary：

| 目标事件/秒 | 计划 / 接收 | 生成队列丢弃 | 含排空秒数 | 含排空接收事件/秒 | ACK p99 | 生成→观测 p99 | 阶段结论 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 500 | 15,000 / 15,000 | 0 | 30.010 | 499.841 | 24.493 ms | 7.328 ms | 通过 |
| 2000 | 60,000 / 60,000 | 0 | 30.439 | 1971.133 | 47.645 ms | 913.744 ms | 通过 |
| 5000 | 150,000 / 120,220 | 29,780 | 51.748 | 2323.176 | 43.125 ms | 22,041.239 ms | 失败 |

5000 档实际生成速率约 4999.906 事件/秒，因此这次已不是第2次“供压不足”的同一种结果。生成队列丢弃和排队延迟暴露了此配置下的压力边界。虽然三档 `errors=0`，且结束时两个消费组 lag 都为 0，缺失的 29,780 个事件仍不能被算成成功；2323.176 只是该失败运行的接收速率，不能作为通过的容量承诺。

## 十万实体：完整预热与过期快照分别记录

第4次接收并核验全部 100,000 份保留快照，预热生成耗时 32.845 秒，含排空为 52.462 秒，其中消费者排空为 19.406 秒。`sourceStaleAfterSeconds=30`，完整核验记录 `warmupExpiredSnapshots=100000`。过期快照仍可读取其身份和版本，所以该结果证实完整保留事实，却不证实十万实体在核验时全部在线、新鲜。

之后的 500 事件/秒、30 秒阶段接收 15,000 / 15,000，errors/drops/最终两个 lag 均为 0，含排空接收速率 499.830 事件/秒，ACK p99 23.395 ms，抽样生成→观测 p99 30.495 ms。本轮没有十万实体的 2000/5000 档结果，不把一万实体结果搬过来。

## 生成器模板缓存：先测实际挂载路径

第2次的 under_offered 促使检查负载发生器。每条事件重新读取并解析 fixture，在保留 run 目录的只读挂载及符号链接路径下开销明显。现在每个来源只读/解析一次模板；每条事件创建独立映射，更新身份、版本、时间与事件 ID，生成后仍执行 Normalize，不跳过六类格式和业务校验。

[generator/summary.json](../generator/summary.json)记录 Linux、2 CPU、512 MiB、无网络、`GOMAXPROCS=2` 下的 `BenchmarkLoadDriverFixture`，每次 `benchtime=1s`，各运行三次。被测操作包含生成及 Normalize，表中是三次的中位数：

| fixture 路径 | 每事件读盘/解析 | 缓存模板 | 范围说明 |
| --- | ---: | ---: | --- |
| 镜像直接 `/app/testdata/sources` | 26.006 µs/op | 16.065 µs/op | 镜像内路径 |
| 实际保留 run 的 `/work/testdata/sources` | 743.360 µs/op | 14.466 µs/op | run 目录只读挂载，符号链接目标仍在镜像内 |

实际挂载路径三次读盘结果为 723.662 / 743.360 / 967.133 µs/op，缓存为 14.464 / 15.055 / 14.466 µs/op。该路径的中位数约降低到原来的 1/51.4，支持“每事件文件读取/模板解析是供压路径瓶颈”的判断；它不是服务端端到端容量提高 51.4 倍的证明。CPU top 同时包含 disk/cached 子基准，也不直接测量阻塞墙钟时间。原始微基准文本、六类格式/模板不变性测试及哈希在 [generator 目录索引](../generator/generator-manifest.json)中。

## 百万初始化：redo 与大 INSERT 的诊断过程

第5次的 [MySQL 警告记录](20260913T140130-13ad51c7/mysql-redo-diagnostics.txt)在 `06:02:19Z` 至 `06:03:26Z` 多次出现 MY-014084：redo 空间无法回收，log_checkpointer 落后。[redo-diagnosis.json](redo-diagnosis.json)记录当时查询的 redo 容量为 104,857,600 字节（100 MiB）、buffer pool 256 MiB、`max_allowed_packet=64 MiB`。失败基准库的绑定计数为 0，符合该事务未成功提交，不能说前面处理过的实体已经初始化成功。

诊断把十份来源 JSON 单独插入再回滚：JSON 总字节为 31,801,970，服务端区间为 0.8741 秒，包含 docker exec、传输、查询及回滚的端到端区间为 2.296 秒。这个复现没有重放此前百万行事务的持续写入压力，只能说明大来源批次单独可成功、其 JSON 体积低于 max_allowed_packet；不能排除完整事务内的 JSON、redo 或 I/O 成本。该诊断是带工具调用关联的现场转录，没有伪造独立原始诊断日志哈希。

第7次明确配置 redo 1,073,741,824 字节（1 GiB），保留 MySQL 1 GiB 内存和 2 CPU 上限，仍初始化失败。新增批次诊断定位为 `operation=insert start=1000000 rows=10 parameter_bytes=31802820 elapsed=5.063214548s`：百万实体批次后，最后十条 Source 记录仍聚成一次约 31.8 MB 的写入。这里参数字节含 binding key 和 JSON，与上面仅 JSON 的 31,801,970 字节不是同一个口径。单次耗时接近原数据库 I/O 的 5 秒预算，但归档只保留底层错误类型，不能单凭它断定唯一根因；可以确定，扩大 redo 本身没有让本轮百万初始化通过。

当前 [syncBindings 实现](../../../internal/tasks/migrations.go)保留 500 行预查边界，并对 INSERT 的 binding key + JSON 参数增加 **4 MiB 软字节预算**。超过预算的单行独立发送，不裁剪 JSON，也不拆开整个 Seed 事务；所有语句仍在同一个事务内，冲突或失败会回滚。它限制一条语句的批量大小，不能限制完整事务的锁、undo/redo 和总注册表内存，也不是百万初始化已经通过的证据。

## 第8次：初始化通过，突发预热消费未追平

[20260913T144121-9bfdab63](20260913T144121-9bfdab63/summary.json) 使用新建的专用数据卷、4 MiB 参数软预算和 1 GiB redo；仍保持原容器 CPU/内存上限和事务语义。数据库 Seed 从 06:41:56 到 06:45:15 UTC，约 199 秒，随后 Entity 和 Ingest 启动成功。

百万不同实体的首次上报全部获得 Kafka 持久确认：人员、无人机、车辆、机器人各 200000，传感器和设施各 100000；发布错误和生成队列丢弃均为 0。预热未限速，生成约 292.747 秒、3415.923 条/秒；包含排空等待约 322.945 秒。ACK 的 100000 条抽样 p99 为 53.466 ms。

**最终 failed。** 额外等待 30 秒后，投影仍积压 472332 条、历史仍积压 326211 条。全量快照核验没有执行（WarmupSnapshots=0），后续 500 条/秒档位也没有执行（Phases=null）。因此本轮证明百万注册初始化与百万首次上报持久接收已经跑通，不能证明百万状态全部可查询、持续 500/s 或百万并发通过。零观测样本和零已核验过期快照不是零延迟或全部新鲜。

预热按十条来源流尽快发送，与 `--rates=500` 独立；30 秒排空从发布/观察结束后起算，另受剩余预算限制。没有放宽验收门槛。runner 中验证器、Ingest、Entity 共用 4 CPU / 3 GiB，注册表也分别占用内存；本次 cgroup OOM kill=0、外层未超时、退出码=1，专用依赖停止成功。

下一步若继续研究容量，应分别测有界预热速率下的实体基数，以及固定基数下的消费端吞吐，并定位消费批处理、数据库写入与注册表内存。改变预热方式或资源上限须作为新的实验条件记录，不能覆盖本次失败。本轮没有增加分库分表或宣称已经解决全部百万规模瓶颈。
