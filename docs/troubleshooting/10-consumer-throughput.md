# 消费进程增加后，吞吐仍没有明显提升

## 现象与定位

同样资源下，Entity 从一个进程增加到三个，完成吞吐只改善约 9%，仍未达到当次 2,000 events/s 验收。先查看 [原始对照与限制](../../verification/2026-09-13-consumer-comparison/README.md)，不能把该比例作为通用扩容结论。

检查分区分配后发现，一个进程原本已运行三个分区工作协程。增加进程只重新分配这三个分区。临时计时进一步发现逐条同步提交 Kafka 位点成本较高，历史采样的进程级锁还覆盖了 MySQL 事务。

## 处理办法

位点提交改为每分区最多 100 条、健康循环下每 100ms 刷新成功前缀；失败记录不能被越过，取消后的未提交记录允许重放。还试验了历史按实体串行、公共锁只保护 map 和预算的候选。该候选功能和竞态测试通过，但两轮固定资源压测均出现生成队列丢弃，因此已恢复原有历史实现，只保留批量提交。完整设计与回归命令见 [消费性能说明](../operations/consumer-performance.md)。

先跑正确性测试，再在相同资源、负载、持久化设置下分别对照原实现、仅批量提交和两项优化。不要同时启动构建、集成测试和性能负载，否则无法区分代码收益和资源争用。

## 本次验证中遇到的环境与夹具问题

- MySQL 容器初始化会启动一个只提供 socket 的临时实例。`mysqladmin ping -h localhost` 可能提前报告健康，runner 通过 TCP 建库却失败。规模 Compose 改用 `127.0.0.1` TCP 探测，等正式服务监听。
- 保留缺口演练通过 Docker Compose 执行测试主题截断。自定义测试项目名后，终端也要设置 `COMPOSE_PROJECT_NAME`，否则测试会去找默认项目而失败；不能因此跳过缺口测试。
- 测试夹具先调用一次 `time.Now()` 生成发生时间，再调用一次生成过期时间，在 Linux 纳秒精度下可能不满足严格的过期关系。应由同一个发生时间加 30 秒构造过期时间，并先验证夹具合法性，再断言业务结果。
- 并发候选可能携带上一秒取得的时间稍晚进入预算短锁。新窗口建立后，旧时间戳不能再次重置预算；晚完成的失败事务也不能退款到新窗口。

这些步骤分别解决启动、测试目标、测试输入和并发预算问题。性能报告必须保留失败尝试，不能只归档通过的结果。
