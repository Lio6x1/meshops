# MeshOps 全面复核、代码注释、问题记录与 UI 方案

## 用户确认的工作范围

用户先要求估时，随后明确同意开始四项工作，并允许按实际需要使用子 agent：

1. 对外部评审的 28 项问题逐条判断，并独立重新检查整个项目，修复实际缺陷，验证完整流程。
2. 为现有手写代码补充详细且必要的注释，解释业务规则和技术边界。
3. 在本地保存问题记录，包含现象、复现、根因、解决办法和验证方法。
4. 提供前端 UI 设计方案，包含关键页面线框、交互状态和现有接口对接说明。

本轮基线为 `641bf62`。此前已经上传完整工程并通过 [GitHub Actions](https://github.com/Lio6x1/meshops/actions/runs/34676260613)，旧评审中的搜索未装配、未进入 Git、从未运行远端 CI 不能直接沿用。通过 CI 也不排除未覆盖的业务缺陷。

## 范围与技术约束

- 六类模拟实体；人员、无人机、车辆、机器人执行固定 inspect；传感器和设施仅上报状态。
- 每个实体一个权威来源，操作员指定执行实体，由可信绑定确定执行方。
- 根目录是完整参考工程；Z01—Z10 是渐进课程。修复影响旧阶段时同步同一缺陷，不向早期阶段倒灌后续功能。
- 生成的 Protobuf 文件由锁定工具生成；完整文件答案和分步清单由维护脚本发布。
- 机器令牌、明文回环传输、本机 Compose、单实例等边界必须准确说明；不把 UI 设计稿或模拟执行效果写成已部署生产能力。
- 使用现有 Go/go-zero/gRPC、Kafka、Redis、MySQL、bbolt、Canal、Elasticsearch 技术栈。调整以已复现问题和必要工程约束为依据。
- 代码注释以解释为什么、生命周期、事务与幂等、不变量、单位和失败恢复为重点。测试注释解释所证明的行为；生成代码不手工加注释。
- UI 本轮交付设计与可浏览原型，明确模拟数据；实际 HTTP 接入和前端业务部署另按设计落实，不冒充现有功能。

## 审查与执行方法

并行审查任务、状态/Kafka、边缘运行时；主执行者检查搜索、安全与配置、脚本和 CI、文档与课程、整体装配。审查后给子 agent 明确文件所有权，主执行者统一处理跨模块接口、课程发布和真实依赖验证，避免并发运行会停止同一依赖的故障脚本。

每个条目记录当前代码证据、判定、处理和验证。无法复现的性能判断通过实际 EXPLAIN 或有边界的测量确认。更改业务行为前建立失败回归；保留失败记录，修复后运行相关回归，再做项目整体验收。

## 交付与验收

- `docs/review/2026-09-12/assessment.md`：28 项原问题及新增发现的核对记录。
- `docs/troubleshooting/README.md` 及问题条目：可持续维护的本地排错知识库。
- 更新后的手写代码、对应测试和同步教材，以及注释阅读入口。
- `docs/ui/README.md`、设计说明和独立可浏览原型：页面、状态、权限、数据与接口映射。
- 最终验收记录：普通测试、真实依赖并发测试、必要故障复验、真实 CDC、EXPLAIN、协议检查、文档链接、Git 下载指纹及新学习目录的完整演示。
- 结论区分代码实现、实际测试覆盖、设计方案、未覆盖边界；不使用旧压测证明新增性能。
