## 1. 需求背景

公司或实验室内部存在多个边缘网关、仿真系统和业务集成服务，它们持续产生人员、无人机、地面车辆、巡检机器人、固定传感器、充电站等设施的实体状态。各来源的数据模型、更新时间和可信度不同，操作端难以统一查看；任务创建、下发、执行和取消也缺少统一状态与审计链路。

需要建设一个内部实时协同平台：对不同实体类型提供统一接入、状态视图、查询与订阅，并为具备能力的实体可靠地创建、下发和跟踪任务。首批自行提供人员和无人机两类模拟来源与格式适配，其他类型后续复用公共链路，完整实体范围见[实体类型目录](../../entity-catalog.md)。

本项目不直接接入或管理硬件，不负责 MQTT、OTA、飞控、图传和设备影子。上游边缘系统负责硬件协议和初步数据处理，本平台只处理应用层实体事件与任务。

## 2. 产品定位

- 内部平台，不向公网开放数据接入能力。
- 服务对象是边缘网关、仿真平台、算法服务和其他业务集成系统；项目提供一个最小参考边缘网关验证接入协议与弱网恢复。
- 主要使用者是操作员、集成方和系统管理员。
- 国内部署为主；本地 Docker Compose 用于功能、压测和故障演练，不代表真实生产高可用。
- 核心提供有限历史抽样；统计报表等增强后续按需评审。

## 3. 核心业务不变量

1. 同一来源的同一事件重试不能产生重复业务结果。
2. 同一实体的旧版本状态不能覆盖新版本状态。
3. 实时订阅允许丢失中间状态，但重连后必须能恢复到最新快照。
4. 任务创建成功后必须可查询，不得出现“返回成功但任务不存在”。
5. 任务消息采用至少一次投递，执行端必须通过业务幂等键防止重复执行。
6. 任务状态只能按状态机合法迁移；取消、完成和超时并发时只能有一个有效终态。
7. 所有任务变更必须可审计。

## 4. 规模与技术指标

先用 2 个来源、20 个实体、2 个订阅者和一种 inspect 任务验收闭环。以下是后续压力阶梯，完成验证前不得描述为线上成绩。

| 指标 | 目标 |
| --- | --- |
| 集成数据源/边缘网关 | 20～100 |
| 活跃实体 | 1万～10万 |
| 稳态状态事件 | 1,000～5,000 events/s |
| 重连补报突发 | 20,000～50,000 events/s |
| 实时订阅者 | 常态20～50，压测200 |
| 任务创建峰值 | 50～100/s |
| 状态事件受理延迟 | P99 < 100ms |
| 最新状态可见延迟 | P99 < 200ms |
| 核心任务接口目标 | 99.9%；本地以故障测试证明行为，不宣称生产SLA |

压测必须记录机器配置、依赖版本、分区数、消息大小、生产者并发、消费者数量和原始结果。

### 恢复时间目标（校招项目压测验证）

| 故障场景 | 恢复目标 | 测量标准 |
| --- | --- | --- |
| Consumer宕机重启 | Lag从峰值恢复到<1000条 < 5分钟 | 从进程启动到Lag稳定在基线 |
| Redis清空后重建 | 窗口覆盖所有待恢复实体时，10万快照重建目标 < 10分钟 | 从开始消费到Redis命名空间切换完成 |
| Kafka积压消化 | 1小时积压数据追平 < 15分钟 | 从消费速率恢复到Lag清零 |
| 多网关集中重连 | 按序限速追平，记录积压期间新事件延迟，不承诺实时 P99 | 补传期间新事件的可见延迟 |

以上目标用于校招项目演示故障恢复能力，实际值以压测为准。

## 5. 需求拆解

### 5.1 接入与事件受理

- 参考边缘网关使用bbolt保存未确认事件，通过累计ACK水位安全删除，并在链路恢复后按连续序列限速补传，新事件追加队尾。
- 参考网关生成两类原始 JSON，经人员/无人机适配器转换为标准化实体事件，不实现MQTT、UDP、真实硬件协议和自研WAL。
- 集成方注册、凭证认证和权限范围。
- gRPC Bidirectional Streaming 批量上报；低频管理接口可使用 Unary RPC/REST。
- 限制连接数、消息大小、批次大小和发送速率。
- 事件包含 `event_id`、`source_id`、`entity_id`、`entity_version`、`occurred_at`、`received_at` 和 `schema_version`。
- Kafka 写入成功后才返回已受理；多租户按 `tenant_id + entity_id` 作为消息 Key，保证同一租户实体进入同一分区。
- 客户端超时重试可能产生重复消息，下游必须幂等。

### 5.2 统一实体状态

- Entity 由稳定标识、Ontology、Components、Provenance 和版本信息组成。
- 人员、无人机、车辆、机器人、传感器、设施采用按需组件；并非所有实体都有电量、运动状态或执行能力。新增类型须验证字段映射、组件缺省语义以及查询/订阅复用，不能只新增类型标签。
- 第一版每实体只有一个权威 source_id，绑定配置包含 source_generation；多类型实体采用可选组件，不做跨来源融合。
- 状态投影器只接受更新版本，原子更新 Redis 最新快照。
- 支持实体过期、下线和删除事件。
- Redis 是可重建的最新状态视图，不是长期事实存储。

### 5.3 实时订阅

- 第一版按认证租户内的显式实体 ID 列表订阅；类型、区域和来源过滤仅保留契约字段，暂不实现。
- 每个订阅者使用有界队列，禁止无界内存增长。
- 慢消费者优先合并同一实体的中间状态；持续过载时断开并返回可识别原因。
- 第一阶段单实例使用进程内有界队列；实时订阅服务多实例后才启用Redis Pub/Sub。Pub/Sub只负责低延迟通知，不承诺持久化、ACK或断线补发。
- 同步流程为“先登记和缓冲 -> 发送逐实体快照 -> SNAPSHOT_END -> 增量去重”；重连重新同步，不使用单一全局实体版本。

### 5.4 任务调度

第一版由操作员指定执行实体，只支持 inspect 模拟任务；调度范围限定为可靠下发与执行跟踪，不实现自动最优分配、优先级排序或工作流编排。

- 创建任务需要业务幂等键；任务与 Outbox 在同一 MySQL 事务提交。
- TaskCatalog 定义任务类型、参数约束和适用执行方。
- Outbox投递器将未发布事件投递到 Kafka，并可安全重试。
- 任务分发器消费任务事件，执行下发、ACK、超时、重试和死信处理。
- 任务状态使用显式状态机和 `status_version` 乐观锁。
- 同一任务可能被重复投递，但不得被重复执行。

### 5.5 历史与回放

- Kafka 在实际保留窗口内提供重放；完整恢复还要求窗口覆盖实体最新事件与墓碑，缺失时需来源全量补报或检查点。
- 历史抽样写入器按固定周期或显著变化将轨迹抽样写入 MySQL；任务节点保存在任务审计中，触发关联轨迹抽样作为后续增强。
- 第一阶段支持按 `entity_id + 时间范围` 查询基础轨迹。
- Kafka 不作为用户查询数据库；MySQL 不保存全部高频原始事件。
- Elasticsearch 仅在需要时间、地理区域、实体类型和属性的复杂组合检索时引入。

### 5.6 可观测性与运维

- 指标：接入速率、Kafka生产延迟、消费延迟、Consumer Lag、快照更新延迟、订阅扇出、慢消费者数量、Outbox积压、任务重试和死信。
- 日志：结构化、脱敏，贯穿 `request_id`、`event_id`、`trace_id`、`entity_id` 和 `task_id`。
- Trace 覆盖 gRPC、Kafka生产/消费、Redis、MySQL和任务下发链路。
- 支持优雅关闭、健康检查、限流、超时、重试退避和依赖故障演练。

## 6. 数据量与保留策略

假设单条状态事件编码后约 300B，在 5,000 events/s 下原始负载约 129.6GB/天（未计副本和协议开销）。因此不能把全部高频事件永久写入 MySQL。

- Kafka：开发环境按容量配置短期保留，时间上限24小时、每分区约1GiB，任一限制均可能先触发清理；生产方案再根据磁盘、复制因子和合规要求计算。
- Redis：每个实体只保存最新快照，并设置生命周期策略。
- MySQL轨迹：从小数据集开始按周期或显著变化抽样，设置总写入预算与保留期；1Hz 不是全局 4% 采样。
- MySQL任务与审计：长期保存，按业务要求归档。
- Elasticsearch/ClickHouse：后续扩展，不进入核心写链路。

## 7. 安全需求

- 集成方凭证与 `source_id` 绑定，不信任请求体声明的身份。
- 操作员、集成方和管理员使用不同权限模型。
- 接口限流、消息大小限制和字段白名单防止资源耗尽。
- 外部URL、文本和扩展字段均视为不可信输入。
- 密钥只通过环境变量或Secret注入，不进入仓库和日志。
- 当前无 Agent 入口；保留 P5 作为后续独立评审项目。

### 多租户隔离（校招项目简化模型）

本项目采用简化的多租户模型，重点展示隔离机制而非完整的多租户平台能力：

- **tenant_id 来源**：从认证凭证（API Key或JWT）解析，不信任消息体声明
- **Kafka分区键**：`tenant_id + entity_id` 保证同租户同实体有序
- **Redis命名空间**：Key格式为 `tenant:{tenant_id}:entity:{entity_id}:snapshot`
- **查询隔离**：所有查询和订阅接口强制按认证租户过滤，不允许跨租户访问
- **MySQL隔离**：`entities`、`tasks`、`entity_history_samples` 均包含 `tenant_id` 列并建立复合索引
- **第一阶段不支持**：跨租户实体关联、租户配额、租户级性能隔离

**校招项目实施建议**：第一阶段可以硬编码2-3个测试租户，重点演示隔离机制和权限校验；完整的租户管理（注册、计费、配额）不进入核心实施范围。

## 8. 验收标准

1. 可重复演示“上报 -> Kafka -> 最新快照 -> 实时订阅”的完整链路。
2. 可重复演示“bbolt积压 -> 断线恢复 -> ACK水位 -> 限速补传 -> 安全删除”的参考网关闭环。
3. 可重复演示“创建任务 -> Outbox -> Kafka -> 下发 -> ACK -> 完成”的完整链路。
4. Redis清空后，在保留窗口覆盖完整最新状态的受控数据集上验证重建；窗口外冷实体需全量补报。
5. 消费者宕机恢复后从已提交位点继续，重复消息不破坏状态。
6. 并发创建、取消、完成和超时测试证明任务状态不变量。
7. 慢消费者、Kafka积压、MySQL不可用和Redis不可用均有明确降级行为。
8. 压测结果和故障演练保存原始证据；未验证能力不得写入简历。
9. P3 若选择动态多实例扩展，再验证 etcd 租约注册、Watch 发现、异常摘除、长连接倾斜与重连。

## 9. 非目标

- 硬件协议、MQTT Broker、设备管理、OTA、飞控和图传。
- 完整原始轨迹永久存储。
- 不在第一阶段部署 Elasticsearch、Kubernetes 或服务网格。
- 模拟真实军用系统或宣称未经验证的生产规模。
- 当前核心范围不实现 LLM Agent。
