## 1. 架构目标

本平台面向边缘网关、仿真系统和业务集成服务，解决多源实体状态汇聚、实时订阅和任务可靠调度。系统不直接管理硬件，不采用 MQTT，不实现设备影子。

实体设计范围包含人员、无人机、地面车辆、巡检机器人、固定传感器和充电站等设施。首批人员/无人机模拟来源仅用于最先跑通链路；四个服务按接入、状态和任务职责划分，各类型共用查询、订阅及适用的任务通道。新增类型通过来源适配和组件演进接入，不按实体类型拆服务。类型专有字段的现状与边界见[当前实现与课程入口](../../../README.md)。

架构的核心不是“堆中间件”，而是根据数据语义拆分两条链路：

- 状态链路追求吞吐、顺序、削峰、短期回放和低延迟最新视图。
- 任务链路追求事务一致性、至少一次投递、幂等执行、状态机和审计。

## 3. 部署单元与边界

第一阶段保持有限拆分，代码按领域分包，进程按负载和故障边界拆分：

| 单元 | 职责 | 核心依赖 |
| --- | --- | --- |
| 接入服务 | 集成方认证、流控、协议校验、Kafka生产 | Kafka |
| 实体服务 | 状态投影、快照查询、实时订阅、历史抽样 | Kafka、Redis、MySQL |
| 任务服务 | 创建/查询/取消任务、状态机、Outbox | MySQL |
| 任务分发器 | 消费任务事件、下发、ACK、重试和死信 | Kafka、任务服务 |
| 最小参考边缘网关 | 两类原始模拟数据与适配、bbolt持久化缓冲、ACK水位、断线重连和限速补报 | bbolt、gRPC |
| 执行方模拟器 | 模拟任务接收、ACK、执行、失败和重复投递 | gRPC |
| 操作端命令行 | 查询、订阅、创建与跟踪任务 | gRPC |

状态投影器、历史抽样写入器和实时分发器初期可作为实体服务内部独立工作协程运行；有独立扩缩容证据后再拆进程。Outbox投递器初期可属于任务服务，但必须有独立生命周期和指标。

不保留仅用于”展示微服务”的空网关服务。认证、限流和流式接入属于接入服务；面向操作端的查询与命令由对应领域服务提供。

### Kafka消费者组织（校招项目配置）

| Consumer Group ID | 职责 | 消费Topic | 并发实例 |
| --- | --- | --- | --- |
| `entity-projector` | 状态投影到Redis | `entity-state-events.v1` | P0-P2单实例，P3可扩展 |
| `history-sampler` | 历史抽样写入MySQL | `entity-state-events.v1` | 单实例（校招项目简化） |
| `realtime-notifier` | 触发实时订阅通知 | `entity-state-events.v1` | P0-P2与projector共用协程；P3独立验证 |
| `task-dispatcher` | 任务下发与跟踪 | `task-events.v1` | P2单实例，P3可扩展 |

**设计原则**：
- 不同职责使用独立Consumer Group，避免相互影响消费进度
- 相同职责的多实例共用Consumer Group，由Kafka自动分配分区
- 第一阶段 `realtime-notifier` 与 `entity-projector` 在同一进程内协作，复用消费位点；只有出现明确的延迟分化证据后才拆分独立消费
- `history-sampler` 允许一定延迟，但校招项目为简化运维保持单实例

## 4. 状态事件链路

### 4.1 事件受理

1. 集成方建立 gRPC 双向流。
2. 服务端从连接身份确定 `source_id`，不信任消息体中的身份声明。
3. 校验字段、Schema版本、批次大小和速率。
4. 使用 `tenant_id + entity_id` 作为 Kafka Key，写入 `entity-state-events.v1`。
5. Kafka达到配置的 ACK 条件后返回 `accepted`；这只表示事件已持久化受理，不表示Redis和历史表已经更新。

推荐生产者配置以可靠性优先：`acks=all`、有限重试、幂等生产者；开发环境仍需验证Broker故障时的超时和错误语义。

#### gRPC流式RPC生命周期（校招项目关键验证点）

| 场景 | 行为 | 验证方法 |
| --- | --- | --- |
| 客户端正常关闭 | 客户端调用 `CloseSend()`，服务端完成已缓冲批次处理，返回最终累计ACK后关闭流 | 断点调试与日志确认ACK完整性 |
| 服务端主动关闭 | 过载/认证失效/版本不兼容时返回明确gRPC状态码（`RESOURCE_EXHAUSTED`/`UNAUTHENTICATED`/`FAILED_PRECONDITION`） | 限流触发、凭证过期测试 |
| 网络中断 | 客户端检测到 `EOF` 或连接错误后，指数退避（初始1s，最大30s）+ 抖动（±20%）重连 | 断网恢复演练 |
| 流空闲超时 | 应用层无消息计时负责流空闲关闭；MaxConnectionIdle 只限制没有活动 RPC 的连接 | 长时间无数据发送测试 |
| 单批次失败 | 返回错误且不越过缺口推进 ACK；客户端重试当前批次，非法数据须修复后继续 | Kafka临时不可用测试 |

**校招项目简化**：不实现完整的流式健康检查（如周期性Ping/Pong）；依赖gRPC keepalive和TCP保活机制。

### 4.2 顺序与幂等

- Kafka只保证同一分区内有序，不保证全局有序。
- `tenant_id:entity_id` 固定作为Key，使同一实体通常进入同一分区。
- 生产重试和消费重平衡可能产生重复事件，所有消费者都按至少一次语义设计。
- 状态投影器比较 `entity_version`；旧版本直接忽略，相同版本同事件视为重复。
- 第一版每实体绑定一个权威来源与 source_generation；只比较合法来源代际内的 entity_version，同版本不同内容拒绝。来源迁移由管理配置提升代际，不比较不同来源局部计数。

### 4.3 最新状态投影

状态投影器消费事件并原子更新 Redis：

- 保存实体快照、最新版本、更新时间和来源。
- Lua脚本或事务保证版本判断与更新不可分割。
- 更新成功后发布轻量变更通知；通知只包含定位快照所需字段。
- Redis Pub/Sub 丢失不影响Kafka事实事件和Redis最终快照。
- Redis清空时降级查询，在新视图代际重建；保留窗口须覆盖所有最新事件和墓碑，否则需来源全量补报或检查点，不能直接声称全量恢复。

### 4.4 实时订阅与背压

- 服务端先登记并缓冲增量，再逐实体读取快照，发送 SNAPSHOT_END 后排空缓冲；重连完整同步，详见框架导航。
- 第一版仅支持 1—100 个实体 ID；类型、来源和区域过滤暂不支持。
- 每个订阅者使用有界队列。
- 队列满时合并同一实体的中间更新，只保留最新版本。
- 持续过载时服务端断开并返回 `RESOURCE_EXHAUSTED`，客户端退避后重新同步快照。
- 不为每个实体创建独立Redis channel；实例订阅有限的主题，在进程内维护订阅索引。
- 第一阶段单实例通过进程内有界队列分发；只有实时订阅服务多实例后才启用Redis Pub/Sub。

### 4.5 最小参考边缘网关

- 标准化实体事件先写入bbolt本地持久化缓冲，再尝试上传。
- `pending_events`按本地单调序列保存Protobuf字节；元数据保存`gateway_epoch`、`next_sequence`和`confirmed_sequence`。
- 中心只有在Kafka持久化受理后才返回最高连续ACK水位；网关不得越过缺口删除事件。
- 链路恢复后按连续序列限速补传，新事件追加队尾；第一版不承诺积压期间实时延迟。
- 网关设置最大缓存字节数、最老事件年龄和明确的磁盘满行为。
- 不实现MQTT、UDP、真实硬件适配器、OTA、设备影子和自研WAL。

#### bbolt容量管理策略（校招项目配置）

| 参数 | 默认值 | 行为 |
| --- | --- | --- |
| 最大缓存大小 | 1 GB 或 100,000 条事件（先到为准） | 超限时拒绝新事件写入，触发ERROR日志和指标告警 |
| 最老事件年龄告警 | 1 小时 | 超过后触发WARN日志，提示链路可能长期中断 |
| 磁盘满行为 | 拒绝写入 + 返回错误 | 不自动删除未确认数据；依赖运维介入或链路恢复 |
| 离线压缩触发条件 | 文件大小 > 初始2倍 **且** 已确认事件占比 > 80% | 在停止写入并关闭相关句柄后用 bbolt.Compact 生成新文件，校验与安全替换；异常保留原文件 |
| 补传速率限制 | 500 events/s（令牌桶） | 按序发送；发送速率必须高于持续产生速率才能追平 |

**实施注意事项**：
- bbolt是嵌入式B+树数据库，文档统一称"本地持久化缓冲"，不得描述为"自研WAL"
- 删除操作只标记页面可复用，不会自动缩小文件；离线压缩需要写入暂停和额外磁盘空间，耗时须实测，不预先保证 100ms
- 断网时间与缓存容量须按单网关产生速率计算；10万条缓存按100条/秒仅约1000秒，恢复时间按净消化速率计算
- 磁盘满拒绝新写入并告警，不覆盖未确认事件；降低模拟产生速率后再恢复

## 5. 任务可靠链路

### 5.1 创建任务与Outbox

在同一个MySQL事务中：

1. 使用 `idempotency_key` 唯一约束创建任务。
2. 写入初始任务状态和审计记录。
3. 写入Outbox事件。
4. 提交事务后返回任务ID。

Outbox投递器轮询未发布记录，发送到 `task-events.v1`。发送成功后标记已发布。标记失败会导致重复发送，因此消费者必须幂等；不宣称跨MySQL和Kafka的恰好一次。

#### Outbox生命周期管理（校招项目配置）

| 阶段 | 状态 | 保留策略 | 清理机制 |
| --- | --- | --- | --- |
| 待发布 | `published_at IS NULL` | 无限期保留直到发布成功 | 年龄 > 7天触发告警，转入人工处理队列 |
| 已发布 | `published_at IS NOT NULL` | 保留24小时用于排查和重放 | 定时任务每小时清理 `published_at < NOW() - 24h` 的记录 |
| 发布失败 | `retry_count > max_retries` | 保留并告警 | 不自动删除，等待人工介入或问题修复后重置 |

**实施要点**：
- Outbox表需要复合索引：`(published_at, created_at)` 用于清理查询
- 投递器查询条件：`WHERE published_at IS NULL AND next_attempt_at <= NOW() ORDER BY id LIMIT 100`
- 校招项目可以在故障演练中展示"Kafka停机2小时、Outbox积压5000条、恢复后10分钟清空"的场景
- 24小时保留期允许面试时演示重放和幂等性验证

### 5.2 下发、确认和重试

- 任务分发器先将待发命令持久化再提交位点，通过同进程 ExecutorService.ListenTasks 服务端流下发，回报走 TaskService.ReportTaskStatus。
- 执行方以租户内稳定 execution_key（第一版为 task_id）持久幂等；attempt 仅表示传输尝试，重试不改变业务执行键。
- 下发成功不等于执行成功；必须区分已持久化、已派发、已确认、执行中和终态。
- 可重试投递失败持久化 next_attempt_at，由有界 worker 到期发送；超过上限进入死信。Kafka 主题本身不实现延迟计时。
- Consumer Offset只能在业务处理达到明确安全点后提交。

### 5.3 状态机与并发

建议状态：

```text
CREATED -> DISPATCH_PENDING -> DISPATCHED -> ACKED -> EXECUTING
                 |                |                      |
                 +-------> REJECTED                SUCCEEDED / FAILED

回报先到时 DISPATCH_PENDING 也可合法进入 ACKED。
取消请求先设 cancel_requested，确认停止后才进入 CANCELLED。
非终态可条件更新为 TIMED_OUT；不证明执行方实际停止。
```

- 更新请求携带 `expected_status_version`，角色限制与完整迁移表见[当前实现与课程入口](../../../README.md)。
- SQL使用条件更新：`WHERE task_id=? AND status_version=? AND status IN (...)`。
- `affected_rows=0` 表示版本冲突或非法迁移，必须重新读取后返回确定错误。
- 取消先设置 cancel_requested 并发布取消命令；执行方确认停止后才成为 CANCELLED。完成、取消确认和超时以首个合法终态提交为准，迟到结果另存审计。

## 6. 数据存储

### MySQL

- `integration_sources`：接入方元数据与权限范围。
- `entities`：稳定实体元数据，不承载全部高频状态。
- `entity_history_samples`：按实体和时间查询的历史抽样。
- `tasks`：任务当前状态。
- `task_status_history`：任务状态时间线。
- `outbox_events`：待发布领域事件。
- `consumer_dedup`：通用消费去重，清理期限不能套用于执行方 inbox。
- `task_dispatches`：Dispatcher 拥有的持久待发记录及到期重试。
- `task_execution_reports`：Task 拥有的回报去重与迟到结果审计。

### Redis

- `tenant:{tid}:entity:{eid}:snapshot`：Hash 保存快照、版本、来源代际与过期信息。
- 版本与快照同键原子更新；删除保留墓碑防止旧事件复活，内存策略 noeviction。
- 有界的查询缓存、限流计数和会话状态。
- Pub/Sub频道按事件大类或租户分层，不按每个实体无限创建频道。

### Kafka

- `entity-state-events.v1`：实体状态事件，Key为`tenant_id:entity_id`。
- `task-events.v1`：任务领域事件，Key为`task_id`。
- 重试到期时间保存在 MySQL task_dispatches，不设置延迟主题。
- `task-dlq.v1`：超过重试上限或不可处理的事件。

分区数、复制因子和保留期属于部署配置，必须由压测和容量计算决定，不在文档中假装存在唯一正确值。

## 7. 历史回放与Elasticsearch边界

系统内部回放与用户查询是两个能力：

- Kafka重放：从时间戳或Offset重新消费，用于快照重建、逻辑修复和新消费者补数据。
- 业务轨迹回放：历史抽样写入器将抽样轨迹写入MySQL，接口按`entity_id + 时间范围`查询。

第一阶段不部署Elasticsearch。只有需要”时间 + 地理区域 + 实体类型 + 动态属性”的复杂组合检索时，才增加独立ES消费者和索引。ES始终是派生查询模型，可从Kafka保留数据或长期历史事实重建；如果源数据已超过保留期且未持久化，就必须明确无法全量重建。

### 历史抽样策略（校招项目第一阶段）

**抽样触发条件**（满足任一成为候选，再经过年龄、白名单和预算限制；具体见[实施规格C10](../../implementation/contracts.md)）：

| 条件类型 | 判断标准 | 示例 |
| --- | --- | --- |
| 时间周期 | 距上次抽样 ≥ 1秒 | 1Hz基线采样率 |
| 位置显著变化 | 与上次抽样位置距离 ≥ 50米 | 适用于移动实体（无人机、车辆） |
| 速度显著变化 | 速度变化 ≥ 20% 或方向变化 ≥ 30° | 机动检测 |
| 状态变化 | `status` 字段变化；注册后的entity_type不可通过遥测修改 | 起飞/降落、在线/离线 |
| 任务关键节点（增强） | 本版保留task_event枚举，不触发轨迹抽样 | 创建、执行、完成等节点由独立任务审计记录 |

**数据模型**：
```sql
entity_history_samples (
  id BIGINT AUTO_INCREMENT,
  tenant_id VARCHAR(64) NOT NULL,
  entity_id VARCHAR(128) NOT NULL,
  occurred_at TIMESTAMP(6) NOT NULL,
  sampled_at TIMESTAMP(6) DEFAULT CURRENT_TIMESTAMP(6),
  event_id VARCHAR(128),
  snapshot JSON NOT NULL,  -- 完整状态快照
  sample_reason ENUM('periodic', 'position', 'velocity', 'state_change', 'task_event'),
  INDEX idx_entity_time (tenant_id, entity_id, occurred_at)
)
```

**校招项目实施边界**：
- 第一阶段不实现自适应抽样算法（如高速时加密采样、静止时降频）
- 不实现轨迹压缩算法（如Douglas-Peucker）
- 单实体单日抽样量估算：1Hz基线 + 机动事件 ≈ 86400 + 500 ≈ 87k条/天
- 10万实体按1Hz全天约86.4亿条，超出本项目 MySQL 范围；第一版限制参与历史采样的实体数并设置总预算
- 1Hz 是每实体周期，不等于全局4%采样；必须给出实体数、单实体频率及变化触发比例，再记录实际 MySQL 写入量

## 8. 一致性与故障语义

| 故障 | 系统行为 |
| --- | --- |
| Kafka不可用 | Ingest拒绝新事件并快速失败；不得返回已受理。任务保留在MySQL Outbox等待恢复。 |
| Redis不可用 | Kafka继续保留状态事件；最新状态查询明确降级，防止无限回源MySQL。恢复需重放覆盖的最新事件或来源全量补报。 |
| MySQL不可用 | 任务写入快速失败；状态事件仍可进入Kafka，但历史抽样积压。 |
| 状态投影器宕机 | Kafka产生Lag；恢复后从已提交位点继续，版本检查保证幂等。 |
| 任务分发器宕机 | 任务事件保留；恢复后继续消费，执行端幂等防止重复执行。 |
| Pub/Sub断线 | 在线通知可能丢失；发现通知断线或版本缺口后主动触发完整同步，并定期校验版本，不能等客户端偶然重连。 |
| Outbox重复发送 | 消费者按task_id/event_id幂等；不得产生重复任务。 |

## 9. 可观测性

- Ingest：连接数、事件速率、拒绝数、Kafka生产耗时和错误率。
- Kafka：分区吞吐、Consumer Lag、重平衡次数、重试和死信数量。
- Entity：投影延迟、版本拒绝数、Redis命中率、快照重建进度。
- Realtime：订阅者数量、扇出倍数、队列深度、合并更新数、慢消费者断开数。
- Task：Outbox积压、下发延迟、ACK延迟、状态冲突、重试和超时。
- 全链路：`trace_id`、`event_id`、`entity_id`、`task_id`进入日志和Trace；具体ID不得成为Prometheus高基数标签。

## 10. 测试与证据

### 正确性

- 重复、乱序、旧版本和Schema不兼容事件。
- Outbox重复发送、消费者重复消费和进程崩溃边界。
- 任务创建幂等、非法状态迁移、取消/完成竞态。
- 快照重建与历史抽样查询。

### 性能

- 稳态1k、5k events/s逐级加压。
- 重连补报20k、50k events/s短时突发。
- 20、50、200订阅者扇出与慢消费者。
- 优化前后比较Kafka Lag、P99、CPU、内存、Redis写入和MySQL写入量。

### 故障演练

- Kafka Broker、Redis、MySQL、状态投影器、任务分发器分别停机与恢复。
- Consumer Group重平衡。
- Outbox积压后恢复。
- Redis清空后重建。
- 客户端断流、指数退避和集中重连。
