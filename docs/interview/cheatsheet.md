## 30 秒介绍

> 我的项目叫 MeshOps，是一个多源实体实时协同与可靠任务下发平台。它来源于联培期间接触的多实体协同需求和对 Lattice 实体、任务模型的调研。目前接入六类模拟实体，提供实时状态、历史查询、巡检任务下发和任务搜索。后端使用 Go、gRPC、Kafka、Redis 和 MySQL，重点处理异构数据统一、断线补传、重复消息和任务状态一致性，并配有网页和 Docker 演示环境。

## 技术分工

| 技术 | 用来解决什么 |
| --- | --- |
| Go / go-zero / gRPC / Protobuf | 服务装配、类型契约、内部调用与流式传输 |
| Kafka / Redis Lua | 事件持久化与重放、当前状态原子版本投影 |
| MySQL / Outbox | 任务、审计、待发事件同事务保存 |
| bbolt | 断网待发队列、执行方命令与模拟结果持久化 |
| Canal / ES | 任务搜索增量同步、分页、引导与重建 |
| Argon2id / 个人会话 | 带盐密码哈希、可信 RPC 身份、事务内认证版本更新及撤销 |
| HTTP/SSE / Vue / Docker | 浏览器操作、持续状态推送、成套演示 |

五个业务进程：Ingest、Entity、Task、Dispatcher、Search；另有浏览器网关。模拟器与工具不算业务微服务。

## 五个亮点，选择自己能解释的例子

1. **统一实体**：公共字段＋类型组件；电量未知和电量为零不同；一个实体绑定一个权威来源。
2. **可靠状态**：bbolt 保存未确认事件，重连补传；Redis Lua 原子处理来源、版本、身份和内容，旧数据不覆盖新状态。
3. **可靠任务**：任务/审计/Outbox 同事务，稳定执行键与投递尝试分开；持久收件箱保存模拟结果，再精确重试回报。
4. **可恢复搜索**：MySQL 是事实来源，CDC 异步更新 ES；完成标记、版本和恢复起点防止半份索引被当作就绪。
5. **个人身份与撤销**：用户名/密码登录，角色来自数据库；事务内增加认证版本、删除会话并记审计，HTTP/RPC 拒绝旧令牌，网关取消 SSE。

账号细节：Argon2id 使用独立 16 字节盐、64 MiB/3 次迭代/并行度 1、32 字节输出，限制密码输入、哈希参数和计算并发。浏览器 Cookie 与内部 RPC 令牌不同；SHA-256 只索引高熵随机令牌。管理事务还重验调用者有效会话，不能仅信任请求入口已解析的 Principal。[账号操作与恢复](../operations/accounts.md)。

## 当前可引用数字

10000 混合实体、10 个来源，四类移动实体各 2000、两类固定实体各 1000。总计 500 条/秒、持续 30 秒，实际约 499.90 条/秒，ACK P99 1.449ms，抽样可见 P99 3.053ms，错误及最终积压为 0。

这是本机 Linux Docker 中状态链路的限定负载结果；验证器与两个服务共享 4 CPU / 4 GiB，依赖在限额外。不是每个实体每秒上报，不代表系统容量上限，不含网关磁盘、任务执行、订阅扇出与搜索查询并发。[完整条件与证据](../verification/2026-09-12-motion-mixed/README.md)。

## 六个高频追问

- **“多源”是同一实体多来源融合吗？** 当前一个实体一个权威来源，多类来源走统一接入。
- **消息重复怎么办？** 保留稳定身份和版本，消费与执行结果按业务规则幂等；不承诺任意外部动作恰好一次。
- **Outbox 发成功、标记失败怎么办？** 重发同一事件，接收方幂等。
- **取消为什么还可能成功？** 取消是意图，与完成事实存在竞争，不能抹除已经提交的结果。
- **Lag 为零就完整吗？** 不一定；保留窗口缺失的历史不会因为追上末尾而恢复。
- **搜索挂了怎么办？** 任务继续落 MySQL，搜索明确不可用；恢复后追平，必要时按流程重建。

## 当前边界

只实现指定实体的 inspect 下发与执行跟踪，没有自动选执行方、路径规划或全局资源优化。来源和执行方为模拟；单机部署，未验证跨机高可用。已有管理员本机初始化/恢复、操作员管理、首次及本人改密，不含公开注册、邮箱/短信找回、单点登录或生产 TLS。地图最多 30 个演示实体，不承诺一万个点同时渲染。

百万试验已恢复推进：先在 1 万实体增加总写速率，再增加至 10 万/100 万基数；固定六类比例和 10 来源，逐一核验全部预热实体，再运行有界负载档位。独立资源、硬时限和完整失败报告见[规模压测手册](../operations/scale-benchmark.md)。当前没有百万容量通过结论，不能把百万实体说成百万 QPS。

本次普通测试已完成；Windows 真实依赖运行有 216 个顶层 PASS、3 个辅助 SKIP，23 项必需集成门禁 PASS。账号 HTTP 30 项、全栈个人任务审计/取消/CDC、demo 数量/运动/模拟控制及前端 29 项测试与构建均 PASS。最新 Windows 普通测试为 [168 PASS（unit-release）](../../verification/2026-09-13-accounts-scale/unit-release.summary.json)，先前 Linux 普通 race 为 162 PASS；两次普通运行各有 22 项 SKIP（20 项外部依赖门控、2 项 edge/state 崩溃子进程辅助入口），不代表真实依赖 race 通过；百万容量与教程最终验收仍待完成。以上不是新的压测吞吐数字，也不替代个人亲自复现。
