# 实体类型范围与场景参考

修订：2026-09-13。用户已明确“多源”涵盖人员、无人机、车辆、机器人、传感器和设施等多类型实体。本文第 2 节作为平台的实体设计范围；第 3 节保留民用场景参考，不表示已经选定园区或物流业务。设计范围不等于当前实现清单。

## 1. 术语

- **Entity / 实体**：具有身份、类型和状态的业务对象，例如工作人员、无人机、机器人、站点。
- **Source / 数据来源**：上报这些对象状态的系统，例如人员位置服务、无人机运营服务、园区设施平台。
- **Component / 组件**：按需存在的状态块，例如位置、运动、能量、作业能力。统一模型不要求每种实体具有全部字段。
- **Task / 任务**：对具备相应能力的执行方提出的业务请求；一条传感器告警并不自动成为可执行任务。

核心是多类型实体统一接入、实时视图、能力约束与任务协作。多个来源共同更新同一实体、跨来源自动目标识别和数据融合不是第一版必做能力。初版可为每个实体配置一个权威状态来源。

## 2. 平台实体目录

以下六类属于平台设计范围。状态字段按类型逐步实现；表内任务是能力示例，当前任务闭环仍只有 inspect，不承诺实现运送、搬运或充电控制，也不描述任何企业内部协议。

| 类型 | 民用示例 | 典型状态 | 任务能力或关系 |
| --- | --- | --- | --- |
| 人员 person | 巡检员、运维人员、配送员 | 位置、在岗/离岗、空闲/忙碌、技能 | 接收工单、确认到场、回报处理结果；由人员终端模拟确认 |
| 无人机 drone | 园区巡检机、配送机 | 位置、高度、电量、在线状态、作业状态 | 模拟巡检/运送/返回；不实现飞控 |
| 地面车辆 vehicle | 园区服务车、无人配送车、接驳车 | 位置、速度、载荷、能源、可用状态 | 指定地点运送或到场；不实现自动驾驶 |
| 移动机器人 robot | 巡检机器人、配送机器人、AGV | 位置、电量、执行状态、支持能力 | 到点检查、搬运、配送；不实现运动规划 |
| 传感器 sensor | 环境检测点、设备状态探头 | 固定位置、读数、健康状态、更新时间 | 主要产生状态/告警；初版不具备移动或巡检执行能力 |
| 固定设施 facility | 服务站、充电站、取货柜、月台 | 位置、开放状态、占用、可用容量 | 可以只上报状态；具体操作须另有能力定义与执行方 |

区域/建筑可作为引用的空间资源逐步增加。告警、订单、任务分别建模，不为了扩大类型数量全部塞进 Entity。

当前六类原始格式适配、统一状态查询/订阅与模拟来源均已实现；四类移动实体可执行同一种 inspect，传感器和设施只上报状态。类型专有字段见 [交付契约 C02](implementation/contracts.md)，六类运行方式见 [模拟器说明](simulation-map.md)。数据仍为模拟输入，目录中的运送、搬运、充电等关系只是场景示例，不是已实现任务类型。

## 3. 场景候选与公开依据

### A. 园区综合运营（优先建议）

组合：人员、巡检无人机、服务车辆、机器人、传感器与服务站。

腾讯公开的 WeCityX 数字孪生案例包含园区内人、车、障碍物等状态，以及车载和路侧设备的数据接入；腾讯云也公开提供智慧园区方案。这说明互联网企业的相关业务可以容纳多类物理实体，不必局限于车辆管理。上述完整六类组合是本项目的抽象建议，不是声称腾讯案例已经使用全部类型。

- [腾讯 WeCityX：腾讯驶向企鹅岛](https://wecityx.tencent.com/app/news/articles/202662)
- [腾讯云：智慧园区解决方案](https://cloud.tencent.cn/act/pro/park)

演示建议：设施产生异常状态，操作员查看附近具备能力的人员/机器人，向选定对象派发检查任务，执行方确认和回报，所有操作端看到状态变化。当前验证四类执行者的同一种 inspect 闭环，不要求立即实现自动多执行方编排。

### B. 城市即时配送

组合：骑手、无人机、自动配送车、楼宇配送机器人、服务站/取货柜。

美团公开材料提到骑手、自动配送车和无人机的协同；京东公开案例展示服务中心工作人员把包裹交给室内机器人配送，以及机器人与电梯/门禁交互。可以借鉴人机交接和任务结果跟踪，项目无需实现订单交易、支付或全局路径优化。

- [美团：无人机与自动配送车业务介绍（2025-02-21）](https://www.meituan.com/news/NN250221067008264)
- [美团：城市低空物流运营示范中心](https://www.meituan.com/news/MN211221001011207)
- [京东：室内机器人最后 100 米配送](https://jdcorporateblog.com/jd-logistics-develops-indoor-robot-for-last-100-meter-delivery/)

这是多类型运力与交接协作；共享单车跨区域再平衡是不同的问题。若选择此场景，先做可靠任务下发，协作任务依赖和自动分配属于后续阶段。

### C. 仓储物流协同

组合：作业人员、AGV/AMR、叉车、搬运车辆、货架、月台和输送设施。

京东公开仓储案例包含货车、输送线和搬运机器人。此方向容易演示任务占用、状态变化和失败处理，但业务范围容易扩展到库存和完整 WMS；核心阶段仍限定为实体状态和任务协作。

- [京东：加州仓储设施与 CTU 机器人](https://jdcorporateblog.com/inside-look-introducing-jd-coms-newest-self-operating-warehouse-in-california/)

## 4. 实施建议

- 项目名保持“多源实体实时协同与可靠任务调度平台”；介绍中明确“多源异构实体”，同时定义 Source 与 Entity。
- 默认模型保留通用性，具体演示背景作为配置与模拟数据；不同时实现三个行业系统。
- P0 先用一个来源跑通最小状态链路，P1 加入第二个来源并验证人员与无人机的差异；其余类型逐步沿用 P1 的接入/状态机制。P2 负责可靠任务闭环，仅让具备 inspect 能力的实体参与执行。首批两类是开发顺序，不是平台范围上限。
- 人员不强制电量/速度，传感器不强制可执行任务；缺少组件不能按零值误判。
- 同一任务类型可以支持多种实体，也可以只支持一种；由能力校验决定，不写死“所有实体都能 move_to”。
- 仿真统一使用虚构人员和实体数据，公开资料仅作为背景依据，不宣称接入企业真实系统。
