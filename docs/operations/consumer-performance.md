# 消费端性能与正确性边界

最终 Z13 参考实现将消费位点改为有界批量提交。早期教学阶段仍保留较直接的逐条提交；这是学习阶段差异，最终完整答案以 Z13 为准。历史并行候选已实测并暂缓合入，最终工程仍使用原有历史采样锁。

## 为什么加进程不一定明显变快

状态投影与历史采样分别属于不同 Kafka 消费组。每组有 3 个分区，每个分区串行处理；一个 Entity 进程已经可以运行 3 个分区工作协程。增加到 3 个进程会重新分配这些分区，不会把总分区工作协程变为 9 个。共享 CPU、Kafka、MySQL 的成本也不会消失。

## 位点如何合并

实现位于 `internal/bus/commit_batch.go`。每个分区独立记录成功但未提交的条数，以及最后成功记录的下一位点：

1. 应用处理成功后，才把这条记录加入待提交批次。
2. 累计 100 条，或者最早待提交记录已等待 100ms，便同步提交成功前缀的下一位点。
3. 流量停止时，Fetch 使用同一个到期时间醒来，避免少量记录一直不提交。
4. 应用返回错误时，先提交此前成功的前缀，然后持续重试失败记录。失败记录不进入成功批次。
5. 提交暂时失败时，保留同一批次重试，暂停读取更多记录。永久权限错误返回上层；消费者代际失效则退出旧工作协程。
6. 取消或重平衡时不另开后台协程强行提交旧代位点。业务已成功、位点尚未提交的记录由下一代重新处理。

例如偏移量 10、11 成功，12 失败，只能提交下一位点 12，不能提交 13。进程在提交前退出，则 10、11 也可能重放。这里保证的是至少一次处理，依靠 Redis 版本比较、历史去重键和任务事件幂等避免重复副作用，不是 exactly-once。

100ms 是健康消费循环的刷新间隔，不是网络故障或处理函数阻塞时的硬时限。成功但未提交的条数最多 100 条/分区；正在处理的事件在进程中断时也可能需要重新尝试。每个分区只有一个处理/提交协程，不引入并发提交覆盖进度的问题。

## 历史并行为什么暂缓合入

实验中曾将历史采样改为按实体持锁，公共锁只保护缓存和预算。真实 MySQL 测试证明了不同实体的隔离、同实体串行和失败预算归还，竞态检测也通过。但在本机固定资源、2,000 events/s 对照中，两轮均有生成队列丢弃，表现不如仅批量提交。最终代码恢复原有历史实现，避免把未获性能验证的候选当作默认方案。

候选补丁、测试和结果随 [优化对照报告](../../verification/2026-09-13-consumer-optimization/README.md) 归档，不属于最终必抄代码。后续若重新评估，需要分离压测器资源并观察数据库/CPU竞争，再决定锁粒度和写入并发度。

## 跟着课程验证

先完成 Z13 文件复制。在学习工程根目录使用 PowerShell：

```powershell
go test ./internal/bus -run TestCommitBatch -count=1
```

这条命令只验证无需外部依赖的提交边界。完整真实依赖验收按已有启动说明初始化测试依赖，再运行：

```powershell
./scripts/test.ps1 -Integration
```

新增必跑项为 `TestKafkaUncommittedBatchReplaysAfterConsumerRestart`。它在业务成功与批次提交之间取消消费者，随后重新加入相同消费组，确认未提交记录会被重新读取并最终排空；不能把“消息被重复处理”误判成故障，也不能放宽幂等断言。

测试项目使用自定义 Compose 名称时，要在同一 PowerShell 终端设置对应的 `$env:COMPOSE_PROJECT_NAME`，以便保留缺口故障演练定位正确的 Kafka。不要把普通测试中的依赖 SKIP 当作真实故障演练通过。Windows 没有 C 工具链时，`-Race` 需要改在 Linux/Docker 环境执行；普通集成命令不自动提供竞态检测。

性能数字只引用同条件实际报告。优化前的一实例/三实例对照见 [原始对照记录](../../verification/2026-09-13-consumer-comparison/README.md)，不将其数据改写成优化后的成绩。
