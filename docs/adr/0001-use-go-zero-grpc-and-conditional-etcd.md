# ADR-0001：基础技术栈——Go + gRPC + Kafka + Redis + MySQL，etcd 在P3启用

- 日期：2026-08-24
- 状态：已接受
- 决策范围：全部阶段

## 背景

本平台需要处理三类核心负载：多源流式接入、高频状态事件和可靠任务调度。技术栈需要同时支撑高性能 RPC、事件削峰与回放、最新状态缓存和事务事实存储。

问题不是"项目缺少哪些常见中间件"，而是：在这个写密集 + 实时分发场景下，每个组件解决什么问题、替代方案的成本是什么。

## 决策

1. **语言与框架**：Go + go-zero。go-zero 提供微服务骨架、限流、鉴权中间件，zRPC 原生支持 etcd 服务发现和 gRPC/Protobuf，减少自造轮子。
2. **服务间通信**：gRPC + Protocol Buffers。基于 HTTP/2 多路复用和二进制序列化，支持一元、客户端流、服务端流、双向流四种模式，是实时上报与任务推送的基础。
3. **事件主干**：Kafka 保存状态事件与任务领域事件，提供分区有序、消费位点、短期回放和多消费者；详细语义见 ADR-0005。
4. **状态与事实存储**：Redis 保存可重建的实体最新快照；第一阶段通过进程内有界队列分发，多实例后才启用Pub/Sub低延迟通知；MySQL 保存实体元数据、任务、Outbox、审计和历史抽样。
5. **服务发现**：etcd 只在 P3 存在多个动态实例时启用；P0-P2 使用静态 Endpoints。
6. **不同时引入**：Redis Streams、RabbitMQ、NATS；Elasticsearch延后为复杂历史检索扩展。

## P3启用范围（etcd）

P0—P2使用静态Endpoint；P3满足以下条件并启用etcd：

- 服务已经成为独立 gRPC 服务。
- 集成或压测环境中存在至少两个实例。
- 实例需要在不修改客户端静态配置的情况下加入或离开。

P3至少选择一个服务部署两个实例，验证动态注册发现的实际行为。单节点etcd仅用于本地功能与故障语义验证，不宣称生产级高可用。

## 替代方案

### Gin 单进程模块化单体

优点是依赖少、调试简单。缺点是缺少服务边界、RPC 治理和独立扩容场景，无法展示微服务相关能力，也无法体现分布式系统的故障隔离。

### 原生 grpc-go 自建骨架

更贴近底层、展示功底更深，但服务发现、限流、鉴权、优雅关闭等需要自行实现，工作量增加约 30%，一个月周期内风险更高。go-zero 在保留 gRPC/Protobuf 核心能力的同时提供工程化基础设施，收益大于自定义成本。

### 自研 TCP/UDP 协议替代 gRPC

边缘接入场景可能使用更轻的私有协议，但这些协议由上游网关负责。MeshOps的集成接口选择gRPC，以获得Protobuf强类型、HTTP/2多路复用和成熟流式能力。

### Redis 直接承担任务调度逻辑

Redis 只承担状态快照和分发，任务状态机（乐观锁、状态流转、审计）放在 MySQL 与 TaskMgr 应用层。原因：任务需要事务、审计和复杂查询，Redis 缺少这些能力。

### MySQL 读写分离与主从复制

本项目不采用读写分离。理由：读写分离解决"读多写少"场景的读放大，而本项目高频读走 Redis 快照与 Pub/Sub 订阅，MySQL 只保存事实与历史数据，读压力低，没有读瓶颈；系统是写密集，主从复制无法提升写入能力，还会引入主从延迟的一致性代价。若将来出现读瓶颈（压测证明），优先扩展 Redis 层与服务实例，而非主从复制。

## 收益

- go-zero提供服务治理骨架；etcd在P3多实例阶段启用并以测试证据验收。
- gRPC 双向流与客户端流正好匹配上报（写）和任务推送（控制）两种实时模式。
- Kafka吸收补报突发并支持消费者恢复；Redis维护低延迟最新视图；MySQL保证任务和审计事实。
- 每个组件都有不可互换的职责，避免为展示名词重复引入中间件。

## 成本与风险

- 新增 etcd 依赖带来配置、认证、监控和故障模式（见启用条件与验证要求）。
- Redis Pub/Sub 不持久化，属于至多一次通知；可靠事件使用Kafka的至少一次消费语义并要求消费者幂等。
- 单节点本地环境无法证明生产高可用；不宣称生产级集群。

## 验证要求

1. 集成方模拟器通过 gRPC 上报，接入服务正确写入Kafka，状态投影器正确更新Redis。
2. 高频状态不逐条写MySQL；Kafka Lag、快照更新和历史抽样均有指标。
3. P3 双实例注册、发现、负载均衡、异常退出移除有证据。
4. etcd 启动前不可用、运行中断开、恢复三种场景有演练记录。
5. 压测报告从1k、5k events/s稳态逐级加压，并测试20k、50k events/s补报突发；只报告实测结果。

只有上述证据进入仓库后，简历才能写"使用 go-zero/gRPC/etcd 实现分布式协同平台"。
