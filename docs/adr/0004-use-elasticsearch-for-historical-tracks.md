# ADR-0004：Elasticsearch 延后为复杂历史检索扩展

- 状态：历史轨迹 ES 扩展仍未实施；任务搜索已单独采用 ES
- 日期：2026-08-25

## 背景

系统存在两类容易混淆的回放需求：

1. 系统内部事件重放：消费者从Kafka时间戳或Offset重新处理数据，用于恢复快照、修复逻辑和增加新下游。
2. 用户历史轨迹查询：按实体和时间范围读取抽样轨迹，在操作端进行基础回放。

两者都不要求第一阶段必须部署Elasticsearch。旧决策在没有可靠完整源数据的情况下声称ES可从MySQL全量重建，与“高频状态只保存最新值/抽样值”的设计冲突。

## 决策

- Kafka在配置保留期内承担系统内部事件重放。
- 历史抽样写入器将固定周期、显著变化的状态抽样写入MySQL。核心版任务节点由任务审计记录，task_event关联轨迹抽样保留为增强，具体边界见[实施规格C10](../implementation/contracts.md)。
- 第一阶段使用MySQL索引支持 `entity_id + occurred_at` 时间范围查询和基础轨迹回放。
- 早期状态阶段不部署 Elasticsearch；后续 Z10 的任务搜索已使用 ES。本文延后的是历史轨迹复杂检索，不是任务搜索。
- 只有出现时间、地理区域、实体类型和动态属性组合检索需求时，才新增ES消费者和派生索引。

## 重建边界

- 保留期内的数据可以从Kafka重放。
- 超过Kafka保留期的数据，只能从长期保存的MySQL历史抽样或其他归档恢复。
- 如果原始高频事件既不在Kafka也未归档，则明确无法重建完整原始轨迹。
- 不得写“ES始终可全量重建”这类超出事实的承诺。

## 后果

### 优点

- 核心阶段减少一个重型依赖。
- 回放需求与存储语义清晰。
- 将来增加ES时有Kafka消费者这一自然扩展点。

### 代价

- MySQL只适合基础实体时间范围查询，不适合大规模地理聚合。
- 原始高频轨迹的长期保留需要另行设计对象存储、ClickHouse或其他归档方案。

## 启用ES的门槛

同时满足以下条件后再创建新的实施ADR：

1. 已有明确复杂检索接口和查询样例。
2. MySQL方案有可复现的性能或功能不足证据。
3. 已定义源数据保留和索引重建边界。
4. 已设计Bulk部分失败、乱序版本、深分页、Mapping演进和删除同步测试。
