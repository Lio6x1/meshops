# ADR-0002：Redis Pub/Sub 仅用于可恢复的实时通知

- 状态：已修订
- 日期：2026-08-25
- 关联：ADR-0005

## 背景

操作端需要低延迟接收实体最新状态，但可以丢失中间帧；断线后只要能够恢复到最新快照即可。旧版本把 Redis Pub/Sub 同时描述为实时分发与“至少一次”异步消息，这是不成立的。

Redis Pub/Sub 不持久化消息、没有消费位点和ACK，订阅端断线期间的消息无法补发，因此属于至多一次即时通知。

## 决策

Redis Pub/Sub条件式保留：第一阶段单实例使用进程内有界队列；只有实时订阅服务多实例后才启用。启用后严格限制职责：

- 状态投影器成功更新 Redis 最新快照后发布轻量通知。
- 实时订阅服务订阅有限数量的主题，并在进程内根据实体、类型、来源和区域过滤。
- 不为每个实体无限创建Channel。
- 客户端断线重连时先读取最新快照和水位，再继续增量订阅。
- 慢消费者使用有界队列、同实体更新合并和明确断开策略。

以下数据不得只通过 Redis Pub/Sub 传递：

- 任务创建、下发、ACK和状态事件；
- 审计事件；
- 历史索引或统计所需事件；
- 需要断线补发、重试或回放的事件。

这些可靠事件统一进入 Kafka，具体见 ADR-0005。

## 后果

### 优点

- Redis通知链路延迟低，实现简单。
- 丢通知不会丢失Kafka事件或Redis最终快照。
- 明确区分实时可见性与可靠投递。

### 代价

- 客户端协议必须支持快照恢复和版本去重。
- Pub/Sub故障时只能降级，不能宣称无损。
- 需要额外维护Kafka可靠事件链路。

## 验证

- Pub/Sub断开期间持续写入，重连后客户端通过快照恢复最新状态。
- 构造乱序和重复通知，客户端只应用更高版本。
- 慢消费者队列达到上限后内存保持有界，并按协议断开或合并。
