# ADR-0003：按负载与一致性边界有限拆分服务

- 日期：2026-08-25
- 状态：已修订

## 背景

服务拆分应由独立负载、数据所有权和故障隔离驱动，不能只为在简历中展示微服务。旧方案固定拆成Gateway、EntityMgr、TaskMgr，但Gateway只有转发职责，且状态流与任务流的扩缩容方式不同。

## 决策

原状态/任务链路的四个部署单元为：

1. **接入服务**：面向集成方的流式接入、身份认证、限流、校验和Kafka生产。其主要压力是连接、网络与事件生产。
2. **实体服务**：状态投影、Redis快照、历史抽样、查询和实时订阅。内部工作协程先模块化，压测证明需要后再独立部署。
3. **任务服务**：任务事实、状态机、乐观锁、审计和Transactional Outbox。
4. **任务分发器**：消费任务事件、下发、ACK、重试和死信。因生命周期和扩缩容模式不同于任务服务，作为独立工作进程。

Search 已作为第五个业务进程负责任务索引投影与查询；另有 web-gateway 承担浏览器会话、角色、CSRF、HTTP 映射、授权清单和 SSE，不是原方案中只有转发职责的占位网关。集成方模拟器、模拟执行方与操作端命令行是客户端。当前演示未提供 TLS 终止。

## 边界规则

- 每个服务只修改自己拥有的数据表。
- 同步查询或命令通过版本化gRPC接口。
- 跨边界异步协作通过Kafka领域事件，不通过Redis Pub/Sub。
- Redis Pub/Sub仅服务Entity实时通知。
- 内部worker先保持代码模块独立；只有独立扩容、资源隔离或故障隔离收益经过验证后才拆进程。

## 后果

### 优点

- Ingest可按连接和Kafka生产能力扩容。
- Entity与Task的数据语义和故障域清晰。
- 任务分发器故障不阻止任务事实落库，恢复后可继续消费。
- 避免为了“微服务数量”增加无业务价值的网络跳转。

### 代价

- Kafka事件契约和消费者兼容性需要测试。
- 任务服务与任务分发器之间是最终一致，需要清楚区分“已创建”和“已下发”。
- 多实例阶段才需要etcd，核心阶段使用静态Endpoint。

## 验证

1. 接入服务停止不影响已创建任务的查询与状态管理。
2. 任务服务停止不影响状态事件进入Kafka和实体投影。
3. 任务分发器停止时任务保留在MySQL/Kafka，恢复后继续下发。
4. 状态投影器停止时Kafka Lag增长，恢复后快照收敛。
5. 拆分前后保留资源消耗、延迟和故障影响对比，不只证明“能拆”。
