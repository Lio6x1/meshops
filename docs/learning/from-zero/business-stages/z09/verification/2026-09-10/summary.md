## 本轮修复与审查

- 执行方在本地持有 ACKED/EXECUTING 待回报、远端任务已超时的情况下，可以核对权威终态并继续处理后续任务；本地取消墓碑和已落盘执行结果保留。
- 历史过期数据清理从每分钟500条，改为有时间/批次数预算的连续分页清理，积压时短间隔续跑；增加004索引迁移。真实 MySQL 测试验证单轮清理1500条及对应去重键，不将它描述成长期保留压力测试。
- Kafka 保留窗口已删除事实时，Lag 返回明确缺口，消费记录错误日志和低基数计数；影子重建缺少期望实体时不切换。使用真实 DeleteRecords 验证，未将数据缺失当成追平。
- 补充真实进程强杀窗口：网关远端已确认/本地未提交，Redis 已投影/Kafka 未提交，Outbox 已发布/未标记，Dispatcher 已落库/未提交，执行方效果和回报已落盘。另验证专用 Redis OOM、真实 gRPC 慢流、六类鉴权接入及状态类实体拒绝任务。
- 最终定向审查发现的3个 P2 已修复并经失败复现、回归验证：停容器报错仍尝试恢复、允许的压测时长具有排空预算、报告写入失败返回非零退出码。复查未发现这三处仍有 P1/P2；这是定向审查结论，不承诺全项目没有缺陷。

## 故障恢复实测

[faults.json](faults.json) 的四步均观测到预期故障，再完成恢复：

| 故障 | 观测 | 恢复耗时 |
| --- | --- | ---: |
| Kafka 停机 | 发布未被确认 | 34.088秒 |
| Redis 停机 | 查询返回 UNAVAILABLE，Kafka 保留待投影事件 | 3.936秒 |
| MySQL 停机 | 任务查询返回 UNAVAILABLE，恢复后读到原任务 | 4.376秒 |
| Entity 进程强杀 | 查询不可用，恢复后追上停机期间事件 | 27.966秒 |

耗时从开始恢复操作算到功能恢复，包含进程/容器启动和消费追平，不是线上 SLA，也不等于报告中 `RestoredAt - StoppedAt`。原始进程日志保留在报告的 `.local/verification/<run-id>/` 目录。已停止本轮启动的应用进程，专用依赖容器及测试数据保留供复查。

## 性能实测

环境：[machine.json](machine.json)，i7-14650HX、16核24线程、约31.6 GiB内存、Windows 11；Go 1.25.10；本地 Docker Kafka/Redis/MySQL。先逐一核对10000个实体快照，10个来源、3个Kafka分区、每次上报1条，每档30秒。完整输出见 [benchmark.json](benchmark.json)。

依赖镜像为 Kafka 3.7.0、Redis 7.2-alpine、MySQL 8.0；Go 客户端精确版本见 [go.mod](../../go.mod)。每档对应单来源平均10/50条每秒；Ingest、Entity 各1个进程（Entity 内含历史消费），另有1个验收驱动进程，没有订阅客户端，过滤集合不适用。编码消息大小 p99 为289字节。该场景未测服务端内部受理计时点和任务下发延迟，表中 ACK 延迟明确采用客户端计时。

| 提供负载 | 接受条数 | 实际接受速率（含排空） | 客户端至 Kafka ACK p99 | 抽样可见延迟 p99 |
| --- | ---: | ---: | ---: | ---: |
| 100条/秒 | 3000 | 99.89条/秒 | 6.033 ms | 24.329 ms |
| 500条/秒 | 15000 | 498.90条/秒 | 3.934 ms | 78.209 ms |

两档上报错误、生成队列丢弃、观测遗漏均为0；状态投影与历史消费 Lag 最终均为0。分别观测60/60、300/300个采样事件，指标序列数 Ingest 保持46，Entity 从46变为48。最高档结束时两服务 Go 活跃堆分别约16.73/14.66 MiB。

这里验证给定负载下的状态接入链路，没有测出系统最大吞吐。可见延迟每50条抽样，通过独立轮询观察同版本或更高版本，包含轮询延迟；内存为 Go 堆而非 RSS。结果不覆盖网关 bbolt、任务执行、订阅扇出或长时间稳定性，不能写成“全链路500并发”或据此宣称生产容量。
