## Z07-01：先定义任务状态，再写创建接口

先阅读 `proto/common/v1/task.proto`、`proto/task/v1/task.proto`，再创建 `internal/tasks/domain.go` 与 `domain_test.go`。协议提供状态枚举，domain提供允许怎样转移的规则，不能把“枚举中存在”当成“任何时候都能改成这个状态”。

正常过程是 CREATED → DISPATCH_PENDING → DISPATCHED → ACKED → EXECUTING → SUCCEEDED。客户端创建完成通常看到DISPATCH_PENDING；CREATED及其后续变化在同一事务内记录。执行方ACK可能早于Dispatcher回报DISPATCHED，因此规则允许DISPATCH_PENDING直接进入ACKED。

真实的权限分支：

```go
if Terminal(from) {
    return false
}
if role == "dispatcher_service" {
    return to == commonv1.TaskStatus_TASK_STATUS_DISPATCHED && from == commonv1.TaskStatus_TASK_STATUS_DISPATCH_PENDING
}
if role == "system" {
    return to == commonv1.TaskStatus_TASK_STATUS_TIMED_OUT
}
```

1. `Terminal` 先建立终态屏障，已经成功或超时的任务不能被迟到回报改回执行中。
2. Dispatcher只证明下发状态，不能自称任务执行成功。
3. 超时由平台system路径处理，不由任意执行方直接设置。
4. 后面的executor分支分别检查ACK、开始、结果、拒绝及取消需要的前置条件。不要压缩成“只要数字更大就允许”。

`ParseInspect` 校验 duration_seconds为1到60，note不超过256个UTF-8字节；拒绝未知字段、重复字段、null和多余JSON对象。`normalizeCreate` 将参数规范化为稳定JSON，再计算请求hash。字段排列不同不应创建不同业务请求；相同幂等key但实际参数不同必须拒绝。

先读 `TestInspectValidation`、`TestCreateHashUsesDeadlinePresenceNotClock` 和 `TestTaskTransitionAuthorityAndTerminalBarrier`。特别注意默认deadline的hash不能含每次调用的新当前时间，否则一次网络重试就会被误判为不同请求。

## Z07-02：用一个MySQL事务记录任务与待发布事件

依次复制schema、`migrations.go`、`store.go`、`service.go`。它们的完整路径和内容在文件答案中，历史表定义也提前放在schema里，但本阶段不运行实体历史消费者。

阅读 `CreateTask`，按以下步骤画出请求过程：

1. 从context取操作员身份，校验请求并算规范化hash。先查同租户幂等key，已存在且hash相同则返回原任务。
2. 对首次创建检查可信绑定和Entity快照，确认存在、未过期、状态可用、允许inspect且执行方一致。这个远程查询发生在数据库写事务之前。
3. `BeginTx` 开启事务，插入任务。数据库唯一约束负责兜住并发请求，不能只依赖前面的“先查有没有”。唯一冲突后重新查询既有记录并核对hash。
4. `writeAudit` 写状态审计，`persistChange` 更新任务并写Outbox。任何一步错误，defer Rollback撤销本次未提交修改。
5. Commit成功后才返回创建结果。已经Commit后defer Rollback不会把已提交事务撤销。

下面是这里必须理解的Go写法，完整函数见答案：

```go
tx, e := s.db.BeginTx(ctx, nil)
if e != nil {
    return nil, unavailable(e)
}
defer tx.Rollback()
```

`tx` 后面的SQL共享同一个事务连接。若不小心把中间某次写入改成 `s.db.ExecContext`，它可能跑到事务外，破坏“任务与Outbox一起成功”的保证。SQL中的 `?` 用于参数绑定，不把用户字符串拼进SQL。

为什么不直接写MySQL后马上发Kafka？这两次操作可能只成功一个。Outbox把“以后必须发布的事件”与任务存在同一数据库事务里，发布器可以稍后补做。

### Z07-02第二遍：让Outbox重试，但保留原事件身份

复制 `workers.go`。先读 `Run`：Outbox发布和deadline扫描是独立worker，Kafka卡住不能阻止任务超时。WaitGroup只负责等待退出，context负责通知退出。

再逐步读 `publishOne`：

1. 用FOR UPDATE SKIP LOCKED领取可发布记录。NOT EXISTS保证同一任务较早的未发布事件不会被跳过。
2. 写入lease_owner和lease_until，提交领取事务。随后才进行网络发布，避免持有数据库行锁等待Kafka。
3. 读取已持久化payload，使用原event ID发布，成功后带lease_owner条件标记published。
4. 发布成功但标记失败时，下一轮还会发布同一事件。所以Outbox不是“绝不重复”，接收端仍需幂等。
5. 失败保留记录，增加retry_count并设置next_attempt_at。退避有上限，不在无限紧循环里轰炸依赖。

lease是临时处理权，不是分布式事务。worker暂停过久、租约过期后，另一个worker可能接手；带owner条件避免旧worker随意改写新worker的领取记录。

## Z07-03：持久化分发尝试，再通过长连接发送

复制 `dispatcher.go`、`dispatch_worker.go`。Dispatcher消费task事件，用持久记录去重并更新任务镜像；它不能把自己的镜像当作最终执行事实，发送前还会查询Task。

区分三个编号：task ID识别业务任务，execution key识别需要去重的一次执行，dispatch ID识别某次传输尝试。重试会创建新的尝试，但不能改变execution key，否则执行方会以为是新的工作。

`dispatchOne` 的顺序是领取 → 查询权威任务 → 检查绑定、终态、取消及deadline → 持久记录已尝试下发与ACK截止 → 提交 → stream Send。服务在Send前崩溃也会在ACK截止后继续处理这次尝试，不能仅在内存里记一个倒计时。

Send返回nil只代表发送调用成功，不证明执行方已经可靠接收。执行方必须先写inbox，再报告ACKED。ACK超时会按配置安排新尝试；达到自动轮次上限进入DLQ。

`ListenTasks` 根据已认证执行方身份注册流，业务命令只能发给绑定执行方。同一执行方活动流有明确限制，避免两条连接在同一业务身份下不受控地竞争。

## Z07-04：执行方落盘去重，再报告结果

复制 `internal/edge/inbox.go`、`executor.go`及对应测试、CLI和入口。inbox同样使用bbolt，但职责不同于网关上行队列：它保存已经接收的命令、执行结果和待确认的状态回报。

1. `AcceptWithLimit` 校验命令和容量，持久接收后才推进本地状态。相同execution key不能重复产生副作用。
2. `executeOne` 先处理持久化pending report。网络失败重发原回报，不能每次重新生成event ID。
3. 确认ACKED后再报告EXECUTING；模拟inspect结束时，`CommitResult` 在本地事务中写结果与effect计数。
4. 结果已落盘但回报丢失，重启后继续上报原结果，不重新执行。演示的effect_count=1就是这个本地模拟副作用的证据。
5. `StoreReport`先写待报内容，再调用ReportTaskStatus；确认后ResolveReport清除它。不要先清除pending，再尝试网络请求。

这里的“效果一次”仅覆盖课程中与inbox处于同一本地事务的模拟效果。真实硬件动作或外部支付不会自动参加bbolt事务；如果以后接入真实系统，需要对方提供幂等执行键或另设计确认机制。

### 联合检查：取消、超时、DLQ与查询

回到Service里的 `CancelTask` 和 `ReportTaskStatus`。取消请求只持久化cancel_requested并产生事件，不直接承诺设备已停止。执行方收到并处理取消后，才回报取消结果；如果任务已完成，平台保留完成事实。

状态回报带expected status version。服务端核对回报身份、dispatch绑定和当前版本，防止两个并发结果同时修改状态。远程dispatch校验与事务锁的先后顺序也要保留，不能在持有任务行锁时等待一个可能卡住的RPC。

超时扫描通过相同任务事实建立终态屏障。执行方恢复时若还持有过期ACKED/EXECUTING回报，不能永远重试，也不能直接删除：源码先获得明确拒绝，再查询权威任务、确认身份与终态，然后调用RetireRejectedReport。查询失败则继续保留原回报。

DLQ表示本轮传输重试耗尽，不等于业务执行一定失败。人工RetryDLQ必须检查权限、当前任务和已有重试轮次，保留execution key，不能简单复制任务再发一遍。终态任务不能通过DLQ重试复活。

`RetryDLQ` 的事务单独使用 `sql.LevelReadCommitted`，理解这一处时按以下顺序看：

1. `SELECT ... ORDER BY id DESC LIMIT 1 FOR UPDATE` 找到并锁住该任务最新的投递记录，然后才决定能否追加下一次尝试。
2. MySQL 默认的可重复读隔离级别可能在这个范围扫描中持有间隙锁。多个请求同时扫描时，拿到记录锁的请求反而可能被其他请求的间隙锁挡住，无法插入下一条记录，形成死锁。
3. 此事务改用读已提交，保留记录锁，同时避免该范围扫描的间隙锁。唯一投递 ID 和 `uk_dispatch_attempt` 仍保证只插入一个后继尝试；其他请求返回 `Accepted=false`。不修改全局隔离级别，也不依靠单进程互斥锁。
4. `TestA23DurableDLQAndConcurrentManualRetry` 会让十个调用先读完同一个任务，再同时进入重试逻辑，避免网络延迟把并发测试变成顺序执行。验收要求十个请求都正常返回、只有一个被接受，且数据库只增加一轮。

这是发布验收中实际发现并复现的问题，见[发布验证记录](../verification/2026-09-12-git-publication.md)。锁策略可对照 [MySQL 8.0 事务隔离说明](https://dev.mysql.com/doc/refman/8.0/en/innodb-transaction-isolation-levels.html)；读已提交不会消除所有类型的死锁，本例修复的是上述扫描与追加之间的锁冲突。

最后读 `queries.go`：ListTasks和GetTaskHistory按租户查询，游标绑定租户、过滤条件和位置，并经过签名。相同时间戳要用第二排序键继续分页；仅记一个时间会漏掉同一时刻的多条记录。
