# 本轮可靠性修订：每一次“成功”究竟证明了什么

这篇补充讲解对应 Z05—Z09 的可靠性复查。阅读时先问：哪个事实已经落盘，哪个动作还可能没有发生，崩溃后用什么证据继续？示例仍限于课程的六类模拟实体、每个实体一个可信来源和指定目标 inspect，不增加生产集群或真实设备的承诺。

这里链接当前工程的完整源码，解释故障原因和修改后的边界；按阶段搭建仍使用 [Z05](files/z05.md)、[Z06](files/z06.md)、[Z07](files/z07.md)、[Z08](files/z08.md)、[Z09](files/z09.md) 的完整文件答案。当前工程包含后续阶段能力，不能把某个最终文件直接替换进较早阶段。

## 1. 下发意图落盘，不等于设备已经收到

假设任务 T 已创建，Dispatcher 数据库中也有一条 `pending` 投递记录。此时命令可能还在排队，尚未被领取。旧校验只核对任务、执行方和 dispatch 的绑定，就可能接受引用这条记录的执行回报；“存在投递记录”还不足以授权执行状态推进。

现在 [dispatchOne](../../../../internal/tasks/dispatch_worker.go) 先写入 `dispatched_at` 和 ACK 截止时间，提交事务，随后才调用流的 `Send`。[ReportTaskStatus](../../../../internal/tasks/service.go) 要求被引用的投递记录具有有效的 `DispatchedAt`，再进入任务写事务。它表示 Dispatcher 已持久化这次发送意图。

具体推演三种中断位置：

| 中断位置 | 已有证据 | 恢复方式 |
| --- | --- | --- |
| 只有 pending 记录，还未持久化发送意图 | 命令已排队 | 继续领取；不能据此接受执行回报 |
| 意图已提交，Send 前崩溃 | 本次发送意图与 ACK 截止已落盘 | 到期后按原任务安排传输重试 |
| 执行方已写 inbox，ACK 在网络中丢失 | 执行方本地保存命令，平台尚未确认接收 | 重发原回报；再次投递由 execution key 去重 |

`Send` 返回 nil 也不能替代 ACK。它没有证明执行方已经将命令可靠写入本地库。另一方面，ACK 可能早于 Dispatcher 向 Task 回报 DISPATCHED；不能要求任务状态先显示 DISPATCHED，才允许 ACKED。校验持久发送意图可以同时保留这个正常竞态和授权边界。

远程查询放在数据库行锁之外，避免依赖变慢时一直占锁；拿到锁后仍要重新检查本地版本和已接收回报。例如查询任务时看到版本 3，等待期间镜像已更新到版本 4，不能拿版本 3 的结果决定再次发送。对应实现见 [dispatch_worker.go](../../../../internal/tasks/dispatch_worker.go) 与 [service.go](../../../../internal/tasks/service.go)。

## 2. 重试改变传输尝试，不改变执行身份

用一次“无人机检查目标”的任务说明三个编号：

| 编号 | 作用 | 重试时是否改变 |
| --- | --- | --- |
| task ID | 标识业务任务 | 不变 |
| execution key | 标识执行方需要去重的一次执行 | 不变 |
| dispatch ID / attempt | 标识一次传输尝试及其序号 | 新尝试使用新记录 |

例如第一次投递 D1 的 ACK 延迟到达，Dispatcher 已把 D1 放入 DLQ。DLQ 说明自动传输重试耗尽，并没有推翻执行方可能已接收、甚至已经开始执行的事实。

旧的人工重试逻辑可能看到“历史投递仍是 DLQ”，就接受新一轮 execute。现在 [RetryDLQ](../../../../internal/tasks/dispatcher.go) 同时看当前权威任务和锁住的最新投递镜像：已 ACKED 或 EXECUTING 的 execute 不再接受人工重试。若远程查询刚读到旧状态，随后迟到 ACK 推进了镜像，锁内检查仍能阻止这个过时决定。回归场景见 [retry_review_test.go](../../../../internal/tasks/retry_review_test.go)。

这个限制只针对 execute。任务已 ACKED 后仍可能需要把取消请求送到执行方，不能用同一个判断误拦 cancel 重试。历史尝试的迟到回报也仍需按身份、版本、终态和重复回报规则处理，不能把历史记录直接删掉来消除竞态。

执行方依靠 [inbox.go](../../../../internal/edge/inbox.go) 保存 execution key、原命令、结果和待确认回报。[executor.go](../../../../internal/edge/executor.go) 重发待确认回报时保留原 event ID。课程中的 `effect_count=1` 只证明与 bbolt 同事务提交的模拟结果没有重复；真实硬件动作并不会自动加入该事务。

## 3. COUNT 和本页数据要来自同一份数据库快照

假设列表开始时共有 10 个待执行任务。旧的 ListTasks 先执行 COUNT，随后另一个请求插入第 11 个任务，再执行本页 SELECT，就可能返回 `total_count=10`，而本页内容已经来自插入后的集合。两个 SQL 各自正确，组合出来的响应却不对应同一时刻。

现在 [ListTasks](../../../../internal/tasks/queries.go) 显式开启只读、可重复读事务。COUNT 和本页 SELECT 都通过同一个 `tx` 执行，读取同一事务快照；读完并关闭 rows 后提交事务。不要把其中一个查询改回 `s.db.QueryContext`，那会离开这份快照。

保证范围是一次 RPC 的计数与页面一致。翻到下一页是另一次请求，没有跨网络等待一直保留数据库事务。游标仍负责绑定租户、过滤条件和排序位置；它不把多次请求变成永远冻结的数据集。Z08 的实体 ListHistory 是另一条查询路径，不应据此宣称它也获得了跨页数据库快照。

## 4. 最新视图必须识别缺口，抽样历史可以有损

先区分 Redis 最新视图和 MySQL 历史样本：

| 数据 | 用途 | Kafka 出现保留缺口时 |
| --- | --- | --- |
| Redis 最新视图 | 返回实体当前已知状态，保留版本与删除依据 | 无法证明完整时停止严格投影，要求维护恢复 |
| MySQL 抽样历史 | 保存白名单实体的有限时间、有限预算样本 | 允许继续处理仍保留的记录，输出缺口与降级诊断 |

旧最新视图使用宽容消费，并把消费位点放在固定 group 下。如果 Redis 整个视图丢失，而 Kafka group 仍记着“下一条是 100”，直接从 100 继续就会漏掉只在 100 以前出现过的实体。即使 lag 已经为 0，也不能证明视图完整。

现在 [Entity.Run](../../../../internal/state/entity.go) 把 group 绑定到 Redis 的 view generation；组名由 [ProjectorGroupName](../../../../internal/state/recovery.go) 统一计算。新的视图代号使用新的消费组，普通重启保留原代号和已提交位点。没有经过验证的重建证据时，新组必须从 0 开始：若 Kafka 最早只剩 offset 40，严格消费者报告保留缺口，不能悄悄从 40 接着读。

但“永远强制从 0”也不能完成实际恢复。Z09 的 [Rebuild](../../../../internal/state/rebuild.go) 在维护期间固定各分区的 `[Start, End)` 边界，重放到新视图，再用独立 expected manifest 检查实体身份、版本与删除状态。通过后，Lua 把 `verified` 标记和 active 指针一起写入；证据还记录具体 topic 与分区边界。[replayFloors](../../../../internal/state/recovery.go) 只有读到完整、匹配的证据，才允许新组从各分区的 End 继续。

例如分区 0 的重建读取 `[40, 100)`，分区 1 读取 `[20, 70)`。只有独立校验证明这个新视图满足预期，100 和 70 才能分别成为后续消费起点。一个失败的重建也可能留下边界记录，所以“存在 bounds”本身不能授权跳过旧 offset；两个分区也不能共用一个拍脑袋选出的标量起点。

Z05—Z08 尚无这项重建豁免，只实现严格从 0 起步的规则和视图代号监测；完整证据激活留在 Z09。活动 generation 变化后，旧投影器会退出，维护流程重启后读取新证据。短暂 Redis 读取失败只重试并记录错误，不能当成已经发生了视图切换。恢复仍要求暂停写入并准备独立 manifest，不承诺持续写入下的在线无损切换。

历史消费者没有对应的“完整历史重建”证明，所以不能借用最新视图的 End 跳过历史缺口。[history.go](../../../../internal/state/history.go) 本来就有白名单、时间与数量预算；[Kafka 宽容消费](../../../../internal/bus/kafka.go) 遇到缺口会明确记录仍在消费不完整历史的诊断。历史查询结果不能被解释为全部上报事件。

Redis 快照的过期时间也不能替代保留证据。DELETE 版本 10 即使已过期，仍需保留版本和删除标记；否则补传版本 9 可能把实体重新显示出来。`expires_at` 控制业务上是否新鲜，不对整个状态 hash 设置 TTL。

## 5. 订阅校验共享版本读取，发送仍按订阅过滤

假设 100 个订阅者都关注同一个实体。以前每个订阅者周期性读取整个快照，会重复读取相同 payload；广播还可能先深拷贝消息，再发现订阅者根本没关注该实体。

现在 [reconcile.go](../../../../internal/state/reconcile.go) 为同一个 Entity 实例维护一个共享巡检任务：合并订阅者关注的实体，每次只读取各实体的版本元数据，并检查活动 generation。上面这个例子每轮只需要该实体的一次版本读取，随后结合每个订阅者已发送、已知及待发送的版本检查缺口；发现缺口便唤醒流并要求完整重同步。[subscription.go](../../../../internal/state/subscription.go) 在深拷贝前过滤实体 ID，减少无用复制。

这没有把订阅变成逐事件日志。每个实体仍只有有界的 pending 槽，中间更新可以合并，目的是最终把较新的状态送到客户端。初始化、已发送版本、已知版本和 generation 校验仍负责避免倒退或把旧视图伪装成新视图。

生命周期也属于正确性：第一个订阅启动共享巡检，最后一个退出时取消并等待它结束；与此同时新订阅注册，必须能启动自己的有效巡检，不能被旧巡检的收尾误停。相关真实流与并发回归见 [review_test.go](../../../../internal/state/review_test.go)。

## 6. bbolt 加派生索引，保留去重事实

假设 inbox 已积累 10 万条完成记录，现在只有 3 条待处理。如果每次 `PendingKeys` 都扫描、解码全部历史记录，处理这 3 条工作的成本就会随着过去完成的任务不断增长。这是数据规模示例，不是本轮测得的吞吐数字。

[OpenInbox](../../../../internal/edge/inbox.go) 现在区分两类桶：`inbox`、`reports`、`results` 是持久化事实；`inbox_pending` 与 `inbox_active` 是从事实计算出来的索引。`PendingKeys` 只遍历 pending 索引，容量检查遍历 active 索引并在达到容量时停止。状态变化和索引更新在同一本地事务中完成。

启动时仍会完整验证原始记录，然后在一个事务里重建派生索引。因此旧文件可以获得索引，残缺索引也不会被当作事实；重建失败必须回滚。启动允许读取完整历史，不能因此声称整个系统再也没有全量扫描。

完成记录没有因为“已不在 pending 索引”就删除。它们仍是阻止旧 execute 再次提交结果的去重依据。删除派生索引可以重建，删除完成事实却可能失去这种保护。索引优化也不是无限存储问题的解决方案；课程没有顺带引入未经验证的历史清除策略。

## 7. SQL 的 LIMIT 限制结果数，不总能限制扫描量

历史保留规则是：`sampled_at` 或 `occurred_at` 任意一个早于 cutoff，就应清理。例如今天才补传一个很早发生的事件，虽然 sampled_at 很新，occurred_at 仍可能过期。把 OR 改为 AND 会错误保留它。

旧选择条件是两个年龄条件 OR，再 `ORDER BY id LIMIT 500 FOR UPDATE`。不能笼统说 OR 一定不用索引：MySQL 在某些分布下会选择 index_merge。问题是合并、排序或沿主键寻找匹配记录时，找到 500 个结果之前可能检查很多候选，尤其是过期行集中在较靠后的 ID 区间时。

现在 [pruneHistoryPage](../../../../internal/state/history.go) 在一个总预算 500 行的事务中，先按 `sampled_at,id` 选并删除过期行，再用剩余预算按 `occurred_at,id` 处理另一范围。两次顺序分别使用 [原有 sampled_at 索引](../../../../migrations/001_initial_schema.sql) 与 [occurred_at 保留索引](../../../../migrations/004_history_retention_indexes.sql)，本轮不需要新建索引。第一批先删除，使两个时间都过期的同一行不会消耗两次预算；样本与对应去重键一起删除，事务失败则一起回滚。

边界仍是严格早于 cutoff，等于 cutoff 的记录本轮保留。拆分改变的是查找方式，没有改变“任意一个时间过期就清理”的业务含义。每页有界也不等于一次调度必定清完全部积压，生命周期仍需时间预算和后续追赶。

验证查询优化时，应分别准备无过期、少量过期、密集过期三种分布，检查 EXPLAIN 实际选用的索引及扫描行数。只读 SELECT 的测量不能直接当作带锁删除事务的锁数量或生产速度承诺。

## 阅读后自己推演

不必先背所有函数。沿着一个具体事件回答下面几题，再对照源码：

1. 发送意图已提交但 Send 尚未调用，为什么既不能说设备已收到，也不能丢弃本次尝试？
2. 老投递进 DLQ 后迟到 ACK 到达，为什么 execute 和 cancel 的重试判断不同？
3. Redis 视图消失而 Kafka group 位点还在，为什么 lag=0 不能证明恢复完整？
4. 为什么失败重建留下的 bounds 不能直接成为跳过旧消息的许可证？
5. 为什么删除 pending 索引条目和删除已完成 execution key 是两种不同的操作？

本篇解释实现与故障边界，不替代验收结果。普通测试、真实依赖测试、race、故障恢复和性能实验各自证明不同事情；出现 SKIP 或依赖未运行时，不能从命令退出 0 推导出这些场景都已验证。
