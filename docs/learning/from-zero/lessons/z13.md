# Z13｜用 Docker Compose 运行完整成品

这一课把 Z12 的真实 Vue 页面、Z11 的 HTTP 网关、已有五个 Go 业务服务及中间件统一部署。业务逻辑继续使用前面写好的代码，不在容器里另写一套实现。

按 [Z13 完整文件答案](files/z13.md) 创建部署文件、初始化程序和脚本。它包含所有完整参考代码，按清单复制即可；本页解释文件之间为什么这样连接。第一次只是想体验完成品，可直接使用参考工程并按 [完整启动手册](../../../run-fullstack.md) 操作。

## 1. 先区分镜像、容器、卷

| 名称 | 在本项目中是什么 | 停止之后怎样 |
| --- | --- | --- |
| 镜像 | 编译好的 Go 程序、Vue 静态文件和运行环境 | 可以反复创建容器；代码变更需重新构建 |
| 容器 | 根据镜像启动的一个服务进程 | 可停止、删除、重建 |
| 命名卷 | 数据库、消息队列、模拟执行队列和凭证的持久存储 | 普通 Stop/Down 保留；显式 Reset 才删除 |
| Compose | 描述服务、网络、卷和启动关系的配置 | 脚本据此执行一整套操作 |

`compose.demo.yml` 固定项目名 `meshops-demo`。脚本还显式传 `-p meshops-demo -f <绝对路径>`，避免你终端遗留的 `COMPOSE_PROJECT_NAME` 意外把操作指向其他项目。

学习目录和参考目录里的完整演示都使用这个固定项目名，**不要同时从两个目录启动两套同名演示**。切换目录前先从原目录 Stop/Down，确认自己要复用还是明确 Reset 演示数据；不拿另一目录的初始化文件直接覆盖当前卷。

## 2. 先看最终访问路径

```text
浏览器 http://localhost:18090
      │
      ▼
web（Nginx，容器内 8080）
      ├─ /、JS、CSS → Vue 的 dist 静态文件
      └─ /api → gateway:18090
                     ├─ entity:50052
                     ├─ task:50053
                     ├─ dispatcher:50054
                     └─ search:50055
```

只有网页入口绑定宿主回环地址 `127.0.0.1:18090`；数据库、Kafka、ES 和 gRPC 服务通过 Compose 内部网络互通，不需要暴露到宿主。`entity`、`mysql` 这样的名称是网络中的服务名；容器里的 `127.0.0.1` 只代表容器自己，不能拿它访问另一个容器。

`web` 同时加入普通 `frontend` bridge 与 `private` 内部网络：前者用于宿主网页访问，后者用于访问 `gateway`。其他服务只加入 `private`，不因此公开数据库或内部 RPC。只把 web 放进 `internal: true` 网络曾导致本机容器健康、宿主端口却未实际发布；修复与证据见[完整前后端问题记录](../../../postmortems/2026-09-12-fullstack.md#5-容器全部-healthy宿主网页端口却拒绝连接)。

`MESHOPS_NETWORK_MODE=compose-demo` 让已有程序明确采用受控的容器运行模式。默认本机配置仍要求回环地址；不是把所有程序的默认监听改成任意网卡。

## 3. Dockerfile：编译和运行分开

根 `Dockerfile` 有多个构建阶段。读完整文件时先看这段结构：

```dockerfile
FROM golang:1.25.10-bookworm AS go-build
WORKDIR /src
COPY go.mod go.sum ./
```

1. `FROM` 选择编译所需的环境，`AS go-build` 给这一阶段起名字。
2. `WORKDIR /src` 是容器内目录，不是要求你在 Windows 创建 `/src`。
3. 先复制 `go.mod/go.sum` 下载依赖，再复制业务文件；源码变更时能复用未变的依赖层。
4. Go 程序被编译到中间阶段 `/out`，运行镜像只复制结果与必要配置。
5. 后端运行阶段默认使用非 root 账户；初始化容器需要准备专用卷目录，单独指定初始化权限。

Vue 构建阶段使用项目固定的 Node 24.15 镜像，执行 `npm ci` 和 `npm run build`；最终 Nginx 镜像只复制 `web/dist`。浏览器访问演示时不需要宿主再运行 `npm run dev`，容器中也不长期运行 Vite 开发服务器。

`.dockerignore` 决定哪些本地文件不能进入构建上下文，尤其不能把 `.local` 凭证、`data` 队列、`node_modules` 和临时证据塞进镜像。需要修改服务代码时在源码目录改，然后重新构建镜像。

## 4. 初始化为什么不能随便并行

本工程搜索从 MySQL 全量快照接到 Canal 增量日志，必须有明确的边界。`demo-stack.ps1 -Action Up` 的顺序是：

1. 默认构建当前源码镜像。
2. 运行初始化工具的 `secrets` 子命令，只在没有凭证时生成随机值。
3. 等待 MySQL、Redis、Kafka、Elasticsearch 就绪。
4. 停止 Canal 与业务写入进程，进入初始化/维护窗口。
5. 初始化工具执行迁移、注册信息准备、搜索快照与起点校验。
6. 启动常驻服务和模拟器，等待容器健康，并从宿主确认网页入口实际可访问。

完成标记、ES 索引身份和已有位点要一致，不能为了让 Search 启动就手工写 `complete=true`。再次 Up 会复用存储并重新检查，不等于删除重建所有数据。日志和脚本返回码会告诉你当前失败在哪个阶段。

初始化工具与网关职责不同：`cmd/demo-init` 处理容器启动与维护，本身不是浏览器业务接口；`cmd/web-gateway` 接收已认证页面请求，不能远程触发数据库重置。

## 5. 按顺序实际运行

### 第一步：工具和当前目录

先打开 Docker Desktop 的 Linux engine。在已经完成全部课程文件的学习目录执行：

```powershell
Set-Location 'D:\job\golang\projects\meshops-course-lab'
docker version
docker compose version
Test-Path './compose.demo.yml'
```

如果本地学习模式还在运行，先在 Vite 终端按 `Ctrl+C`，再执行：

```powershell
./scripts/stop-web.ps1
./scripts/stop.ps1
```

特别要释放宿主 `18090`，否则 Docker 的网页端口无法绑定。不要终止其他项目的进程。

### 第二步：构建、启动和登录

```powershell
./scripts/demo-stack.ps1 -Action Up
./scripts/demo-stack.ps1 -Action Status
./scripts/demo-stack.ps1 -Action Codes
```

首次拉镜像和编译可能较久；命令失败先停下来查看错误，不连续执行后面的演示。`Status` 看常驻服务状态，`Codes` 在本地显示两种浏览器角色对应的访问码。不要将访问码截图公开。

浏览器打开 `http://localhost:18090`，选择操作员，输入对应访问码。Docker 模式不使用学习目录 `.local/web-secrets.json`；此处的随机凭证由演示专用卷保存。

### 第三步：按真实链路验收

依次查看六类实体、新鲜快照和历史样本；为人员/无人机/车辆/机器人创建 inspect，观察任务权威详情和分发记录；搜索备注确认 CDC 结果；创建较长任务提交取消，区分请求接受和最终取消。

完整点击顺序见 [启动手册第 5 节](../../../run-fullstack.md#5-第一次体验按这个顺序走)。操作员无法查看管理员运行状态和人工重试死信；管理员也不能把任意未失败任务强行当成死信重试。

健康检查只代表进程或依赖就绪，不能代替上述业务操作。等待 `SNAPSHOT_END` 后再创建任务；数据源注册完成不意味着新鲜状态已经到达 Redis。

`Up` 会自动检查宿主 `/healthz` 和网页 `/`，每项超时五秒，均为 `200` 后才提示启动成功。失败会保留容器和卷供排查。宿主入口也可单独检查：

```powershell
(Invoke-WebRequest 'http://127.0.0.1:18090/healthz' -UseBasicParsing -TimeoutSec 5).StatusCode
(Invoke-WebRequest 'http://127.0.0.1:18090/' -UseBasicParsing -TimeoutSec 5).StatusCode
```

### 第四步：观察持久化

记录一个真实任务 ID，正常停止，再启动：

```powershell
./scripts/demo-stack.ps1 -Action Stop
./scripts/demo-stack.ps1 -Action Up -NoBuild
```

重新登录后查询同一个任务，核对任务和历史仍存在。普通重启保留卷中的业务数据、执行队列、搜索数据和访问码；网关内存会话不会跨重启保留。不要因为需要重新登录就误以为所有数据库丢失。

`-NoBuild` 仅跳过镜像构建；首次没有镜像或代码改了，就运行普通 Up。来源模拟器配置的持续时间为 24 小时，长时间演示后应检查来源进程状态与新鲜度，不把退出的模拟来源当成真实设备故障。

## 6. 熟悉运维入口

| 目的 | 命令 | 是否删除卷 |
| --- | --- | --- |
| 构建并启动/重新检查 | `./scripts/demo-stack.ps1 -Action Up` | 否 |
| 同源码再次启动 | `./scripts/demo-stack.ps1 -Action Up -NoBuild` | 否 |
| 看状态 | `./scripts/demo-stack.ps1 -Action Status` | 否 |
| 看任务日志 | `./scripts/demo-stack.ps1 -Action Logs -Service task` | 否 |
| 持续看网关日志 | `./scripts/demo-stack.ps1 -Action Logs -Service gateway -Follow` | 否 |
| 读本地浏览器访问码 | `./scripts/demo-stack.ps1 -Action Codes` | 否 |
| 停止常驻进程 | `./scripts/demo-stack.ps1 -Action Stop` | 否 |
| 移除演示容器/网络 | `./scripts/demo-stack.ps1 -Action Down` | 否 |
| 明确清空整套演示 | `./scripts/demo-stack.ps1 -Action Reset -ConfirmReset` | **是** |

`Logs` 默认最后 150 行。`-Follow` 用 `Ctrl+C` 退出只停止观察。`-Service`、`-Follow` 不能用于其他动作。Reset 缺少 `-ConfirmReset` 时拒绝执行，正常排错先保留日志和数据，不以 Reset 当作“刷新页面”。

完整演示脚本在启动/停止/重置时持有本地锁，防止同一目录并发运行相互冲突的维护操作。锁文件存在不代表锁仍占用；真正限制来自打开文件时的独占句柄。

## 7. 常见失败怎样判断

### 镜像或模块下载失败

若 `docker version` 已正常，但构建提示下载 DNS/连接超时，先确认失败的是 Docker Hub、Go 模块代理还是 npm。不是所有下载失败都能通过修改同一个代理解决。

Go 模块代理确实不可达时，当前构建支持显式覆盖代理来源，例如：

```powershell
$env:MESHOPS_BUILD_GOPROXY = 'https://goproxy.cn,https://proxy.golang.org,direct'
./scripts/demo-stack.ps1 -Action Up
```

此值只影响当前终端启动的构建，默认仍使用官方代理；Go 校验和验证保持开启。不要设置 `GOSUMDB=off` 或关闭证书校验来掩盖下载问题。首次 Compose 构建仍需要实际能访问所用镜像源。

### 页面能打开，操作失败

先检查页面 HTTP 状态：401 重新登录；403 查角色、Origin 与 CSRF；503 查网关后面的服务和依赖。Compose `web` 只负责静态页和转发，Vue 画出了页面不等于 Task 已正常运行。

```powershell
./scripts/demo-stack.ps1 -Action Logs -Service gateway
./scripts/demo-stack.ps1 -Action Logs -Service task
./scripts/demo-stack.ps1 -Action Logs -Service dispatcher
```

搜索有问题再查 `canal` 和 `search`；实体过期查对应 `source-*`、`ingest` 和 `entity`；执行卡住查对应 `executor-*`。保留真实任务 ID、时间和错误，不往 MySQL/ES 手动塞成功记录。

### 换回 IDE 调试

先 `Stop` 完整演示，释放宿主网页端口，再按 [启动手册的本地模式](../../../run-fullstack.md#6-本地学习模式前后端分别怎样启动) 启动课程中间件、Go 服务、网关和 Vite。两套模式的任务数据和访问码不同，不要在新界面查不到旧任务时先判断数据丢失。

## 补充：把模拟开关接到真正的生成器和上传协程

本课完整答案更新 `internal/edge/cli.go`、`simulation.go`，Compose 显式启用 `MESHOPS_SIMULATION_CONTROL=1`。

1. `GatewayCLI` 保留旧的 offline/drain-only/compact 练习语义；正常生成模式且控制开关启用时，创建 Redis Store，进入控制循环。
2. 控制循环初始暂停，读取目标后才决定是否生成与启动 Upload。生成仍先落 bbolt；版本由原事务分配。
3. 收到暂停或断网目标时，取消上传 context，然后等待上传协程返回。这样“实际已暂停”的心跳不会早于旧连接退出。
4. 暂停不再生成；断网模式仍生成。恢复时重新运行 Upload，从本地确认水位补传，不分配新的业务事件代替原缓存。
5. 心跳定期带出队列 Stats、原子发送计数和生成数。Redis 失效时暂停；正常时长到期/取消应成功退出，明确协议失败仍应上报。
6. motion 只作用于模拟数据，`motion.go` 定义四类加速演示路线，以事件时间推进而非以版本推进，所以启用更多实体不会降低路线速度。同一事件会得出同一位置；无时间戳的单元测试样例才用版本兜底。固定传感器与设施不移动；这不是规划算法，也不会让任务执行器依赖地图。

重新 Up 并按[完整演示说明](../../../simulation-map.md)逐步验收，或运行 `scripts/test-simulation.py` 保存实际证据。模式会跨重启保留，结束体验时可点“全部开始上报”。

完整配置现在每类注册 5 个 ID，四类执行器各绑定对应 5 个 ID。控制循环读取 DesiredCount，将它限制在当前来源候选容量内，再由单个生成循环轮流选取前 N 个 ID。数量为 0 时不生成新事件，正常上报模式仍可补传旧缓存。心跳带 activeCount，数量切换不需要重启进程。每来源总速率仍是 2 条/秒，不随数量相乘；30 个混合实体的端到端验收见 `scripts/test-scene-counts.py`。已有环境通过受限增量注册升级，不清库，不重新生成凭证。

## 补充：一万实体的混合压测

最终完整文件增加 `internal/verification/profile.go`。先阅读 `benchmarkSources`：10 个来源每个 1000 个实体，四类移动实体各两个来源，传感器和设施各一个来源。再读 `newLoadDriver`：启动时把注册表映射整理为按来源轮换的目标数组，热路径不反复遍历大 map，也不再硬编码 person ID。只有四类可执行实体注册 inspect，压测本身不执行任务。

接着阅读 `benchmark.go` 的类型统计和逐实体预热检查：不仅数出 10000 个 ACK，还要逐一读到正确 ID、类型和版本的快照。`observeScheduled` 每 50 条轮换抽取不同来源，防止十来源轮询时固定间隔始终只抽中来源 0；对应单元测试要覆盖全部来源。

加载本机依赖后运行 `./scripts/benchmark.ps1 -Profile mixed -Seconds 30`；需要对照时用 `-Profile person`。二者都先预热 10000 个实体，再运行总速率 100/500 条每秒各 30 秒。报告中的 `entityCountsByType`、`warmupSnapshotsByType`、`acceptedByType` 必须与实际生成分布一致。网页演示的 0—5 限制属于另一条控制链路，不影响压测数量。实际结果及环境限制见[验收记录](../../../verification/2026-09-12-motion-mixed/README.md)。
