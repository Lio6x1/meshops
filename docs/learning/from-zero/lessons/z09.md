## Z09-01：在新视图中重放，校验后再切换

先读 `internal/state/rebuild.go` 的ExpectedState、loadExpected、VerifyGeneration，再读Rebuild。重建针对Redis投影，不恢复已丢失的MySQL任务或网关本地库。

1. 记录旧的active generation，要求新generation未使用且命名空间为空。
2. 读取每个Kafka分区的保留起点与当时末尾，末尾是排他边界。先固定所有分区边界，再开始逐个重放，不能边读边无限追新的尾部。
3. 把事件写入新generation，沿用版本、删除和同版本冲突规则，旧视图暂不被替换。
4. 对照独立的expected manifest逐实体检查身份、版本与删除状态。manifest也必须覆盖实际重放中出现的实体。
5. 全部通过后，以旧active值为条件，在同一段Lua中写入verified标记并切换active指针。期间别人已切换则失败，不能无条件覆盖。

实际激活见 [rebuild.go](../../../../internal/state/rebuild.go) 与 [recovery.go](../../../../internal/state/recovery.go) 的 `activateVerifiedView`。脚本同时核对旧指针、building标记以及已保存的边界和topic证据，再发布新视图。失败重建留下的bounds不能单独授权跳过旧消息。

新视图使用绑定generation的新消费组。重启后的 `replayFloors` 校验verified标记、topic和全部分区边界，才允许各分区从本次重建的排他End继续消费；没有重建证据的新视图严格从0开始。切换保证不自动要求上游停止写入，课程恢复仍需要按维护流程暂停写入并确定完整manifest，不能宣传为持续写入下无损在线热切换。

为什么必须有独立manifest？如果Kafka已清理掉某个实体的最后一条事件，重放仍可以“顺利读到末尾”，却根本不知道少了这个实体。用重放结果自己生成期望结果只能得到自证循环。缺失或不匹配必须阻止切换。

## Z09-02：验证失败后的恢复结果

阅读 `internal/verification/faults.go`、`environment.go`及 `scripts/faults.ps1`。验证器既要制造故障，也要等待恢复并检查结果；进程启动成功不等于依赖已就绪，命令退出0也不等于报告中的每个断言通过。

把故障分为三种不同问题：

| 故障位置 | 应检查的事实 |
| --- | --- |
| 消息确认前后断线 | 未确认事件保留；已写入但ACK丢失的事件可重发且幂等 |
| 数据库、Redis、Kafka或业务进程短暂不可用 | 错误向调用者传播，待处理记录保留，恢复后继续处理 |
| 数据已经永久缺失 | 明确发现缺口并拒绝宣称完整恢复，不把暂时重试当成修复 |

Z07的inbox重启结果、终态屏障和pending report恢复属于业务故障测试；Z09的恢复manifest和保留缺口属于数据完整性验证。它们的通过条件不同，不能只写“加了重试保证一致性”。

先执行常规本地和集成测试，再运行故障脚本：

```powershell
Set-Location 'D:\job\golang\projects\meshops-course-lab'
./scripts/initialize.ps1
./scripts/test.ps1
./scripts/test.ps1 -Integration
./scripts/processes.test.ps1
./scripts/stop.ps1
./scripts/faults.ps1
```

故障脚本会管理课程环境并扰动依赖，运行前停止自己的课程服务。具体环境与恢复操作以 [最终工程运行说明](../../../../README.md) 为准，不对其他项目运行任意停止或删卷操作。若脚本失败，先看该次stderr和JSON，修复原因再复验，不覆盖失败报告冒充首次通过。

## Z09-03：测量明确的链路，不只写一个QPS

阅读 `internal/verification/benchmark.go` 和 `scripts/benchmark.ps1`，确定生成什么负载、从哪里计时、何时结束、怎样排空积压。

本课冻结答案的压测使用人员实体。最终 Z13 完整工程再增加六类 mixed 模式和 person 对照；学习本课不要把旧报告理解成混合压测。到 Z13 时用更新后的完整文件和命令重新实测。

```powershell
./scripts/benchmark.ps1 -Seconds 30
```

该测试先核对10000个不同实体快照，再测试100/500 events/s。指标包括实际吞吐、错误、客户端至Kafka ACK延迟、抽样可见延迟、lag及进程Go堆。ACK延迟回答“平台多久接收”，可见延迟回答“多久能从查询看到”，二者不能互换。

每个计时阶段有单独排空预算，超时应失败，不能将仍在后台堆积的数据算作成功处理。百分位也必须说明样本来源；抽样可见延迟不是所有事件都被逐条计时。

已有基线最高提供约500 events/s负载，实际约498.9，不代表系统最大承载能力，也不覆盖订阅扇出、网关落盘或任务执行吞吐。面试时应该说明机器、依赖部署、数据规模、持续时间与测量口径，然后再报数字。

## 最终核对

对照 [A01—A28验收记录](../../../../verification/2026-09-10/acceptance.md)，将每项需求对应到实际函数、测试和结果。原有 [工程验证摘要](../../../../verification/2026-09-10/summary.md) 是参考证据，你新生成的结果单独保存；出现SKIP、故障未恢复或数据缺口时如实标明。

协议变更另运行 `./scripts/verify-proto.ps1`，工具安装版本见答案中的testdata/proto说明。Windows本地没有C编译器时不要声称已经做了race检测；参考记录中的Linux race与普通Go测试分开记。

到这里实现范围是：六类模拟来源适配、可信实体归属、可靠接入、版本投影、实时订阅、状态抽样历史、指定目标inspect、持久分发与执行去重、取消/超时/DLQ、维护恢复和可复现验收。真实硬件接入、算法调度和AI agent属于额外工作，不影响当前后端项目形成完整闭环。

九个阶段均有结束代码，Z04—Z09共有20个文件递进步骤。逐步构建与指定测试用于验证代码和依赖边界；完整故障/性能验收与学生实际理解仍应分别核对，不能混为一谈。
