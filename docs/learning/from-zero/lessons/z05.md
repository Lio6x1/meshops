# Z05｜Kafka 确认与 Redis 当前状态

本阶段解决Z04的重启丢失问题。手工路线按 [Z05-01](steps/z05-01.md)、[Z05-02](steps/z05-02.md)逐步复制并编译，具体输入推演与依赖接线见 [小步骤说明](steps/remaining.md)。完整阶段答案另见 [Z05文件](files/z05.md)。仍在同一个学习目录操作，先停止Z04服务；受管理路线也可一次应用z05后配合阅读。

## Z05-01：先决定什么时候可以告诉网关“收到了”

链路变为：网关发送 → Ingest 发布 Kafka → broker 确认 → Ingest ACK；另一侧 Entity 消费 Kafka → 更新 Redis → 提交消费位点。ACK 时 Redis 可能还没有更新，这叫异步投影，客户端查询可能短暂落后。

依次阅读并复制 `internal/bus/kafka.go`、`retention.go`、`lag.go` 和对应测试。完整代码中的发布器创建如下，片段仅用于讲解：

```go
return &Kafka{brokers: append([]string(nil), brokers...), writer: &kafka.Writer{Addr: kafka.TCP(brokers...), Balancer: &kafka.Hash{}, RequiredAcks: kafka.RequireAll, MaxAttempts: 3, BatchSize: 1, ReadTimeout: operationTimeout, WriteTimeout: operationTimeout, AllowAutoTopicCreation: false}}
```

1. `append([]string(nil), brokers...)` 拷贝地址切片，调用者以后改原切片不会改掉这里保存的地址。
2. Hash 按消息 key 选择分区。Ingest 使用租户＋实体 ID 作为 key，同一实体进入同一分区；不是把所有实体放进一个全局串行队列。
3. RequireAll 等待 broker 所要求的确认。课程单 broker 环境不能由此声称已经实现多机容灾。
4. MaxAttempts 是一次客户端发布调用内部的重试上限，不是网关整个生命周期的重试次数。
5. 禁止自动创建 topic，避免名字拼错后默默写到另一个 topic。课程启动代码显式准备它们。

阅读 `Publish`：它创建有界 context 并等待 `WriteMessages` 返回。取消函数用 defer 调用，成功或失败都释放定时器。这里不能开一个 goroutine 后立即返回 nil，否则 Ingest 会在 broker 确认前发送 ACK。

再读 `consumePartition`，顺序是 FetchMessage → handler成功 → CommitOffsets(offset+1)。Kafka 保存的是“下一条要读取的位置”，所以读完 offset=12 后提交13。handler失败会重试当前记录，不越过它提交后面的记录。每个分区有自己的串行 worker，一个分区的失败不会要求其他分区同时停止。

Redis 已成功、提交位点前进程崩溃时，消息会重新到达。系统接受至少一次投递，通过下一单元的版本规则确保状态不重复产生错误效果。发生再平衡时 generation 用来阻止旧消费者继续提交已失去所有权的分区。

`lag.go` 和 `retention.go` 用于区分“还没追上”与“需要的记录已经被 Kafka 保留策略清掉”。此时只看 lag=0 不足以证明数据完整，具体恢复在 Z09 学习。

## Z05-02：用 Lua 原子地比较并替换当前状态

复制完整 `internal/state/entity.go`，它替换 Z04 的 MemoryEntity。阅读开头 `applyView`，然后看 Go 的 Apply 调用如何传入 KEYS 和 ARGV。不要手动调整参数顺序。

其中的版本分支是：

```lua
local prior=tonumber(old[3]); local incoming=tonumber(ARGV[3])
if incoming<prior then return -1 end
if incoming==prior then
 if old[4]==ARGV[4] and old[5]==ARGV[5] then return 0 end
 return -2
end
```

1. HMGET 已经读出原来的来源、代次、版本、事件 ID 和内容 hash。
2. 旧版本返回-1，调用者将其视为已处理，允许消费位点继续前进。
3. 同版本且身份/内容一致返回0，是幂等重放。
4. 同版本不同内容返回-2，是数据冲突；不能悄悄覆盖。
5. 真正的新版本执行 HSET 并返回1。比较和写入在同一个 Redis 脚本中，避免两个 Go 进程都读到旧值然后乱序覆盖。

Lua 数值比较依赖精确整数范围，所以校验限制 version 和 source_generation 不超过9007199254740991。不能因为 Proto 是 int64 就允许其全部取值进入 Lua double 比较。

为什么不对整个 hash 设置 EXPIRE？假设 DELETE版本10被自动清除，离线网关补传版本9时，系统就失去了拒绝它的依据。状态是否过期用 expires_at 表示，版本及删除标记继续保留。课程 Redis 使用 noeviction，内存不足作为实际错误处理，不能把无声淘汰当作正确的删除流程。

`viewKey` 把 view generation、tenant 和 entity都放进 key。这里的 view generation 是投影目录的代号，与 source generation 不同：前者区分重建出来的整套视图，后者标记实体权威来源的配置代次。

## 完整运行顺序

应用或手工完成 [Z05 文件](files/z05.md)，包括新 compose、两个 YAML 和 `cmd/course/main.go`。先确认 Docker Desktop 使用 Linux engine：

```powershell
Set-Location 'D:\job\golang\projects\meshops-course-lab'
docker compose up -d --wait --wait-timeout 180
if ($LASTEXITCODE -ne 0) { throw 'dependencies not ready' }
. ./scripts/env.ps1
go build -o bin/course.exe ./cmd/course
if ($LASTEXITCODE -ne 0) { throw 'build failed' }
./bin/course.exe serve --role ingest -f configs/server.yaml
```

终端二进入同一目录、载入 env，运行：

```powershell
./bin/course.exe serve --role entity -f configs/entity.yaml
```

终端三进入同一目录、载入 env：

```powershell
./bin/course.exe report --endpoint 127.0.0.1:25251 --source drone_sim --id drone-001 --version 1
./bin/course.exe get --endpoint 127.0.0.1:25252 --id drone-001
```

第一次查询可能还看不到，等待一小段时间再次查询，应返回version=1。停止并重新启动 Entity，然后查询，状态应仍存在。不要在重启实验中运行 `docker compose down -v`，那会删除持久数据，不是在验证服务重启。

接着停止 Entity，保持 Ingest 和 Kafka 运行，上报 version=2。上报可以成功，查询服务暂时不可用。重启 Entity 后它应消费积压并显示version=2。这个实验直接区分“Kafka已经接收”和“查询已经可见”。

运行本地测试可以执行 `go test ./internal/state ./internal/bus -count=1`；依赖环境未设置时某些集成测试会跳过，不能仅凭命令退出0声称故障实验已经做过。上面的真实进程操作才验证本阶段新增的两进程路径。

| 现象 | 检查 |
| --- | --- |
| Docker健康检查失败 | 先看 `docker compose ps` 和对应服务日志，依赖未就绪不启动业务 |
| 上报成功却暂时查不到 | 检查Entity进程、消费错误和正确查询端口，不把异步延迟当丢消息 |
| Kafka故障时上报失败 | 这是预期，不能改成捕获错误后返回成功 |
| Redis错误持续重试 | 先恢复Redis；确认失败记录未被越过提交 |
| Z04的数据不见了 | Z04是内存阶段，不提供自动迁移，重新发送模拟数据 |
