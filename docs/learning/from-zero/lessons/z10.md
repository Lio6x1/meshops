## 开始前：搜索解决什么问题

操作员记得某次巡检的备注包含“东门”，但不知道任务 ID，想结合执行状态和目标实体找回任务。已有 `task get --id` 适合详情查询，`task list` 适合结构化列表；本阶段的 `task search` 搜索任务备注、取消原因和失败原因。

搜索不会把六类实体的全部状态放入 ES，也不负责选择执行方或计算路线。任务创建、状态流转、Outbox 与执行记录仍写 MySQL。ES 是可以重建的查询副本：搜索暂时失败，Task 仍然可以创建和推进任务；搜索返回的状态可能比 Task 详情稍旧。

```text
操作员创建任务 → Task 的 MySQL 事务 → 原 Outbox / Dispatcher / 执行方
                         │
                         └→ binlog → Canal → 独立 Kafka topic
                                                │
                                                ▼
                                           Search 消费者 → ES
操作员 task search → Search RPC → 带租户过滤的 ES 查询
```

这里有两个异步用途：Outbox 发布任务业务事件；Canal 捕获 tasks 表的事实变化，更新搜索副本。它们的 topic 和消费组分开。不能删掉已有 Outbox，再把所有功能都交给 Canal。

先在学习目录运行 `./scripts/stop.ps1`。Z09 数据、`.local` 凭证、模拟器 bbolt 文件和 Compose 卷均保留。不要在另一目录生成新凭证后去 seed 同一套数据库。

## Z10-01：从 Proto 确定功能

打开 [本步精确清单](steps/z10-01.md)，先写 `proto/search/v1/search.proto`，再生成或复制两个 `gen/search/v1` 文件。本步只增加协议，旧服务仍可编译，还没有 Search 进程。

重点读这几行：

```protobuf
package meshops.search.v1;
option go_package = "example.com/meshops-course/gen/search/v1;searchv1";

service SearchService {
  rpc SearchTasks(SearchTasksRequest) returns (SearchTasksResponse);
}
```

1. `package` 是 Proto 命名空间，与其他服务隔开。
2. `go_package` 前半部分是 Go 导入路径，等于 module 加 `gen/search/v1`；分号后指定 Go 包名。它不是 Windows 路径，也不要求访问 example.com。
3. `rpc` 定义一个普通请求/响应接口。搜索分页由下一页游标完成，不需要服务端流。
4. 请求没有 `tenant_id`：客户端不能靠传一个字符串选择租户。服务端从鉴权结果读取租户。

请求的七个字段分别表示关键词、状态、目标实体、创建时间下界、创建时间上界、每页数量、上一页给出的游标。时间采用 `[created_from, created_before)`，例如下界 10:00、上界 11:00 时，恰好 11:00 的任务不属于这一页查询范围。

`page_size=0` 表示默认 20，显式值只能 1—100。`status` 复用已有任务状态枚举，零值表示不按状态过滤。响应里的 `status_version` 用于识别搜索投影所对应的任务版本；它不让搜索结果变成事实来源。

生成工具路径沿用 Z01。可以运行 `./scripts/generate.ps1`；它递归收集 `proto` 下的文件，所以不必手改脚本添加一个文件名。如果暂时没有生成工具，就复制清单中明确链接的生成文件。完成后执行本步的 `go build ./...`。生成包显示 `[no test files]` 正常，这一步尚未验证业务。

## Z10-02：先把搜索包实现正确

按 [本步精确清单](steps/z10-02.md) 创建 `internal/search` 的完整文件。先顺着下面四个单元读实现，结束时执行本步列出的七个指定测试。这些指定测试不需要运行 Docker；真实依赖测试在第三步装配后执行。

### 单元一：把一条数据库变化转成安全的文档

从 `cdc.go` 的 `Document` 开始。这里只列出业务允许查询的字段，不直接序列化整条 tasks 行。`payload` 里只提取通过 inspect 校验的 `note`；不把幂等键、创建凭证或执行结果原文加入索引。

文档 ID 的实现是：

```go
func (d Document) ID() string {
    b, _ := json.Marshal([2]string{d.TenantID, d.TaskID})
    return base64.RawURLEncoding.EncodeToString(b)
}
```

1. `[2]string` 是固定长度为 2 的数组，依次保存租户和任务 ID。
2. JSON 保留两个值的边界。因此 `a:b` 与 `c` 不会和 `a` 与 `b:c` 拼出同一个标识。
3. 这里的内容只包含字符串，JSON 编码不会遇到不支持的值类型；因此忽略该处编码错误。不能推广成所有 `Marshal` 都忽略错误。
4. URL 安全的 Base64 让结果可直接用于 ES 文档路径。编码不是加密，不能用它隐藏密码。

`DecodeCanal` 接收原始字节和预期数据库名，返回一批文档与错误。逐层检查：消息是否过大或不是 UTF-8；JSON 是否有效；数据库、表和操作类型是否符合约定；FULL 行图是否包含必需列；每行类型、任务状态和时间是否可解释。任意一行无效，整批解析失败。

MySQL 配置必须是 ROW/FULL。ROW 表示记录行变化，FULL 表示更新后镜像包含所有列。消费者要构造完整文档，如果只收到变更的两列，就不能假装其他字段为空后覆盖原文档。

Canal 的真实消息中，MySQL ENUM 可能是 `"1"`、`"2"` 这样的序号，而不是 `"CREATED"`。代码同时验证 `mysqlType.status` 中的枚举顺序，再转换序号；不硬猜顺序。对应 `TestCanalMySQLEnumOrdinal`。这也是为什么模拟 JSON 测试通过之后还要跑真实链路。

当前任务没有物理删除功能。tasks 的 DELETE、TRUNCATE、DDL 必须阻断消费并要求检查，不凭空实现“删 ES 文档”，因为旧消息可能让它复活。Canal 会转发部分其他数据库的无数据 DDL，代码只跳过明确不属于任务库、且不带数据行的这类消息。

### 单元二：版本、幂等和 Kafka 提交

阅读 `index.go` 的 `Create` 和 `Put`。索引映射使用 `dynamic: strict`；ID、状态等用 keyword，备注和原因用 text，时间用 date_nanos。keyword 做精确匹配，text 经过分词用于全文查询。当前使用 ES 自带 standard 分词器，未引入中文分词插件，不能声称已经实现中文语义搜索或相关性调优。

`Document.Version()` 返回 `StatusVersion + 1`。MySQL 初始业务版本允许 0，而 ES external version 使用正数，所以统一加 1；查询响应仍返回原业务版本。

假设同一任务的版本先后到达为 `3 → 2 → 3 → 4`：

| 到达情况 | ES 写入和程序判断 |
| --- | --- |
| 第一次版本 3 | 写入成功，applied |
| 旧版本 2 | ES 拒绝覆盖；读取已有版本确认后判为 stale |
| 相同版本 3、相同内容 | 判为 duplicate |
| 相同版本 3、内容不同 | 返回错误，不能把矛盾数据称为幂等 |
| 新版本 4 | 覆盖成功，applied |

HTTP 409 不一定是“成功的重复请求”。代码先确认错误类型是版本冲突，再读取已有文档，对比身份、外部版本和规范化内容。依赖不可用、错误响应或同版本冲突都会向上返回。

然后读 `handler.go`：

```go
docs, err := DecodeCanal(data, h.Database)
if err != nil {
    return err
}
for _, doc := range docs {
    if _, err := h.Index.Put(ctx, doc); err != nil {
        return err
    }
}
return nil
```

这是主流程解释片段；完整代码另有上下文检查、日志和指标。先验证整批，再逐个写入，最后返回 nil。nil 表示“这条 Kafka 消息内的所有行都已处理”，不是“服务收到了消息”。

消费端只在 handler 成功后提交下一条 offset。若一条消息有两行，第一行写成功、第二行失败，整条消息仍重试；再次写第一行会得到 duplicate，第二行继续处理。若 ES 已成功而 Kafka 提交前进程崩溃，也走同样的重复处理。这是至少一次投递加幂等投影，不是跨 MySQL/Kafka/ES 的分布式事务。

### 单元三：查询、租户和稳定翻页

阅读 `query.go` 的 `normalizeFilter`、游标编码/解码和 `Search`，再读 `service.go`。

1. 规范化关键词、时间和页大小，检查输入边界，再计算筛选条件摘要。
2. 从可信身份取得租户，在每一次 ES 查询的 filter 中强制加入 `tenant_id`。
3. 第一页创建 PIT，即查询时点的索引视图。后续页复用同一视图，避免并发更新让简单页码分页重复或遗漏。
4. 依次按创建时间倒序、任务 ID 升序、PIT 内的 `_shard_doc` 排序；下一页用上一页最后一条结果的 sort 值作为 `search_after`。
5. 请求 `page_size+1` 条用于判断是否存在下一页；只向调用者返回规定页数。
6. 游标携带租户、筛选摘要、PIT、排序位置和到期时间，并用服务端密钥计算 HMAC。换租户、换筛选或篡改内容，校验失败。
7. 五分钟到期时间固定，不随每次翻页无限延长。末页或错误时关闭 PIT，用户中途离开则由 ES 到期清理。

PIT 稳定的是搜索副本的视图，不让尚未同步到 ES 的任务提前出现。搜索后要取消任务，仍调用 Task 服务；Task 根据当前真实状态决定是否允许。

`Service` 把非法输入映射为 InvalidArgument，过期搜索映射为 FailedPrecondition，依赖失败映射为 Unavailable。不能把 ES 故障转换成成功返回空数组，否则操作员会把故障误认为“没有任务”。

### 单元四：第一次导入与中断恢复

先看 `snapshot.go`。单纯“查全部任务 → 查当前 binlog 位点”有空档：导入过程中更新的一条任务可能没有进入快照，又落在新位点之前，之后永远不会补回来。

实现采用两个 MySQL 连接：一个持有短暂全局读锁，一个持有一致性快照。顺序是拿锁、读取 binlog 文件和位置、开启 REPEATABLE READ 只读事务、实际读取 tasks 建立一致性视图、释放锁、继续导入。只执行 BEGIN 还不够；第一次一致性读取才确定视图。

释放锁后任务写入继续，新增变化保留在 binlog 中，Canal 随后从刚才的明确起点读取。ES 写入和磁盘标记保存都不占着全局锁。快照事务、解锁和失败回滚必须有清理路径；实际测试会在解锁后更新数据库，确认导入仍读取之前的视图。

再看 `bootstrap.go`。`.local/search-bootstrap.json` 记录完成状态、ES UUID、binlog 坐标和 Kafka 起点。完整快照导入、起点提交全部成功后才写 `complete=true`。写标记用临时文件、Sync 和 Rename，避免直接覆盖时只留下半份 JSON。

UUID 用来区分“原来的索引”和“同名但被重新创建的空索引”。Search 启动、查询和写入会核对它；同名并不等于数据已经恢复。

维护重建还涉及 `rebuild.go` 和 `cdc_maintenance.go`。假设停 Canal 后 CDC topic 的末尾是 100，重建快照替代了前面的历史，恢复时从 100 接收新变化。如果依旧从旧的错误消息 20 开始，重建完成也会再次卡住。因此记录末尾、重建快照、确认末尾未变、重置专用消费组，再开放服务。

只有消费组无成员时才允许重置；Windows 停进程之后需要等待 Kafka 会话过期。若重建过程中 topic 继续增长，说明 Canal 没有保持停止，必须失败。不能把“跳到最新 offset”单独当作恢复——没有对应的完整快照，跳过的就是丢失数据。

### 故障演练与维护

短暂停依赖的实验要求 Task/Search/模拟器运行：

```powershell
./scripts/test-search-recovery.ps1
```

它分别暂停 Canal 和 ES，确认 Task 仍能成功，恢复依赖后搜索补齐。Canal 停止时查询可能成功但数据未更新；ES 停止时查询应明确 Unavailable。这两种现象不能混为同一个“空结果”。

正常的搜索维护命令：

```powershell
./scripts/rebuild-search.ps1
./scripts/demo-search.ps1
```

若原来 Search 在运行，维护完成后自动重启；若原来未运行，先 `./scripts/start-search.ps1`。维护期间不要从另一终端启动 Search 或 Canal。脚本只停止当前目录登记并核实身份的 Search，不按进程名字批量杀其他项目。

专门练习“未完成标记＋ES 索引丢失”，先停止课程应用：

```powershell
./scripts/stop.ps1
./scripts/test-search-rebuild.ps1

./scripts/stop.ps1
```

这条演练会主动删除专用任务索引，不是日常启动步骤。它比较 11 张业务表的校验和，并核对 MySQL 任务数量与重建后 ES 文档数量。若失败，不要手改标记为 complete=true；保留日志，修复原因，再运行重建。

## 从错误找到对应代码

| 现象 | 首先查看 | 应理解的含义 |
| --- | --- | --- |
| Search 启动报 bootstrap incomplete | `.local/search-bootstrap.json`、初始化日志 | 全量阶段没有完成，走维护流程 |
| index was replaced | Search 日志、ES UUID | 同名索引被替换，不应直接继续写成缺历史的投影 |
| CDC validation failed | Search 日志的原因、Canal 日志 | 数据格式或操作不受支持，当前消息不应提交 |
| search group still active | 当前 Search 所有权记录、等待会话过期 | 不允许重置正在消费的组 |
| CDC changed during snapshot | Canal 是否确实停止 | 重建的边界条件不成立，拒绝发布完成标记 |
| FailedPrecondition / expired | 游标是否超过五分钟 | 从第一页重新查询 |
| Unavailable | ES、Search 日志与 `/readyz` | 依赖失败，不能解释为搜索不到任务 |

日志使用 `log/slog`，课程日志位于 `.local/logs/search.err.log`。HTTP 指标在 `http://127.0.0.1:18084/metrics`：观察写入 applied/duplicate/stale/failed、CDC 失败次数和查询耗时。最后成功处理时间在没有新消息时也会变旧，不能单独用它判断系统卡住；计数包含重试，不代表唯一任务数。
