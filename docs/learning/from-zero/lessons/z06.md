前提是Z05已能上报并从Redis查询。本阶段已细化为 [四个可编译步骤](steps/remaining.md)：六类转换、本地队列、补传协议、订阅装配。先从 [Z06-01文件清单](steps/z06-01.md)开始；完整阶段答案另见 [Z06文件](files/z06.md)。仍在同一个学习目录，先停止Z05服务。

本轮可靠性修订：见 [可靠性补充讲解](reliability-review.md)，重点阅读共享订阅版本巡检和过滤后再复制消息；订阅仍允许合并中间更新，不是逐事件日志。

## Z06-01：增加实体类型，保持事件外层不变

先读本阶段 `internal/state/adapters.go` 新增的四个分支和六个 fixture，再看对应测试。已有人员、无人机外，再接入车辆、机器人、传感器、充电站。不要把它们都当成可以执行 inspect 的设备，任务权限下一阶段来自可信绑定。

| 类型 | 原始数据需要处理的差异 | 统一模型 |
| --- | --- | --- |
| person | 人员编号、在岗、技能集合 | PersonState |
| drone | 整数坐标、厘米海拔、毫秒时间、电量 | Location＋PowerState |
| vehicle | 嵌套位置、速度km/h、载荷kg | Location＋Velocity＋VehicleState |
| robot | pose、energy、故障码集合 | Location＋PowerState＋RobotState |
| sensor | measurement中的读数/单位、测量时间 | SensorState |
| facility | 开放状态、总槽位和占用槽位 | FacilityState |

共同逻辑仍是严格解析、原始ID映射、版本与时间、构造事件。类型差异放在适配器和组件校验里，Kafka不用因为新增机器人就再设计一套完全不同的消息处理流程。

## Z06-02：先把事件记在本地，再发出去

完整代码位于 `internal/edge/queue.go`、`uplink.go`、`simulation.go`、`cli.go`。先读 Queue，再读 Upload，最后看 GatewayCLI 怎样组装它们。`cmd/gateway-simulator/main.go` 是入口，不负责实现持久化细节。

队列用 bbolt，这是嵌入进进程的本地数据库。一次事务同时保存新版本与待发送事件，事务失败两者一起回滚。不能先把 version++ 存成功，再另外尝试入队，否则崩溃可能产生难以解释的状态。

按这个顺序理解真实方法：

1. `OpenQueue` 打开文件并检查结构；已有文件损坏返回错误，不创建空文件覆盖掉待发事件。
2. `BindSource` 把队列绑定到来源身份，防止把人员队列拿去给无人机使用。
3. `Generate` 在写事务中分配实体版本并构造事件，`enqueue` 分配队列sequence并保存。
4. `Pending` 读取尚未确认的事件；读取不代表可以删除。
5. `BeginStream` 建立本轮发送边界；`MarkSent` 记录实际发送的范围。
6. `Ack` 检查 epoch、连续确认位置和实际发送边界，只有合法确认才能删除已确认前缀。

假设队列里有101、102、103：服务器只确认到101，断线后保留102、103。若服务器已写入102但ACK丢失，102会再次发送，仍使用原event ID和内容。Z05的版本幂等规则正是为这种正常重试准备的。

本地队列容量是有限的。队列满必须明确失败或施加背压，不能静默丢掉旧数据再声称可靠上报。压缩文件也必须保留原文件和必要状态，不能简单“删库重建”。

## Z06-03：长连接补传与取消

按 [本步文件清单](steps/z06-03.md)加入uplink及完整测试。`Upload`外层负责断线重连和有界退避，`uploadStream`处理一条流。长连接不能套普通一次性RPC的5秒总超时；但也不能忽略context取消。六项指定测试检查ACK丢失、部分确认、非法ACK不删数据、关闭发送后的最终确认以及取消能退出。

## Z06-04：一次初始化，之后推送变化

复制并阅读 `internal/state/subscription.go` 和新增的 Entity 通知逻辑。Subscribe 只接受明确的实体ID集合，其他过滤字段返回 UNIMPLEMENTED，避免协议上有字段就误以为已经支持按区域搜索。

客户端需要分辨数据帧、SNAPSHOT_END和HEARTBEAT。SNAPSHOT_END表示本次初始化结束，不是某个实体状态；HEARTBEAT表示连接仍活着，不应覆盖地图上的实体。

核心缓冲结构是每个实体一个 pending 槽。无人机连续更新版本8、9、10，而客户端还没来得及读取，可以合并为版本10，因为这里承诺当前状态同步，不承诺收到每一帧轨迹。需要历史记录由Z08提供。

真实代码片段：

```go
select {
case s.wake <- struct{}{}:
default:
}
```

1. 真正的数据已经放进受锁保护的 pending map。
2. wake 是容量1的通知通道，告诉发送方“有变化可取”，不是存储全部事件。
3. 如果已有通知，就走 default，生产者不阻塞。因为 pending 仍保存最新状态，这里省略重复通知不会丢掉唯一的数据副本。
4. `take` 在锁内取走本轮pending并重置字节计数；只有流的发送方调用Send，避免多个goroutine并发发送控制帧和数据帧。

pending同时限制实体数量与总字节数；超限会终止订阅，让客户端重连重新初始化，不能任由慢客户端无限占用内存。view generation变化时也要求重连，避免把两套投影的数据拼成同一快照。客户端用sync ID区分本次初始化，用实体版本避免旧状态覆盖新状态。

## 运行与观察

完整基础启动命令同Z05，但地址改为Ingest25351、Entity25352。本阶段先执行：

```powershell
Set-Location 'D:\job\golang\projects\meshops-course-lab'
docker compose up -d --wait --wait-timeout 180
if ($LASTEXITCODE -ne 0) { throw 'dependencies not ready' }
. ./scripts/env.ps1
go build -o bin/course.exe ./cmd/course
if ($LASTEXITCODE -ne 0) { throw 'course build failed' }
go build -o bin/gateway-simulator.exe ./cmd/gateway-simulator
if ($LASTEXITCODE -ne 0) { throw 'gateway build failed' }
```

分别在两个终端运行 `./bin/course.exe serve --role ingest -f configs/server.yaml` 和 `./bin/course.exe serve --role entity -f configs/entity.yaml`。每个终端都先进入学习目录并载入env。

终端三进入同一目录并载入env。下面完整执行六类离线生成、原库补传与查询；第一次运行使用本阶段的新队列，后续运行仍沿用这些文件：

```powershell
. ./scripts/env.ps1
$sources = @(
    @{ Source = 'personnel_sim'; Entity = 'person-001' },
    @{ Source = 'drone_sim'; Entity = 'drone-001' },
    @{ Source = 'vehicle_sim'; Entity = 'vehicle-001' },
    @{ Source = 'robot_sim'; Entity = 'robot-001' },
    @{ Source = 'sensor_sim'; Entity = 'sensor-001' },
    @{ Source = 'facility_sim'; Entity = 'facility-001' }
)
foreach ($item in $sources) {
    $queueFile = 'data/' + $item.Source + '.db'
    ./bin/gateway-simulator.exe --manifest configs/simulation.yaml --source $item.Source --db $queueFile --offline --rate 10 --duration 1s
    if ($LASTEXITCODE -ne 0) { throw "offline generation failed: $($item.Source)" }
    ./bin/gateway-simulator.exe --manifest configs/simulation.yaml --source $item.Source --db $queueFile --endpoint 127.0.0.1:25351 --drain-only --timeout 60s
    if ($LASTEXITCODE -ne 0) { throw "drain failed: $($item.Source)" }
    ./bin/course.exe get --endpoint 127.0.0.1:25352 --id $item.Entity
    if ($LASTEXITCODE -ne 0) { throw "query failed: $($item.Entity)" }
}
./bin/course.exe watch --endpoint 127.0.0.1:25352 --id person-001
```

`@(...)` 是PowerShell数组，每个 `@{...}` 是一条来源到实体的映射；foreach依次执行六次相同流程。离线产生事件只写本地bbolt文件；下一条命令用相同文件补传。查询可短暂落后于ACK，如果found=false，稍后使用该实体ID重新查询，不能把退出0当作已经found=true。

验收时观察三件事：六类查询返回各自组件；离线生成后原队列能drain；订阅先出现SNAPSHOT_END再继续接收状态。早期course watch主动设置15秒截止，结束时出现DeadlineExceeded是该演示命令的边界，不代表收到的初始化失败。

本地边界测试：

```powershell
go test ./internal/edge -run 'TestQueue|TestUpload|TestBackoff' -count=1
if ($LASTEXITCODE -ne 0) { throw 'queue or uplink tests failed' }
```

| 现象 | 应如何处理 |
| --- | --- |
| bbolt文件被锁住 | 同一个队列不能同时被两个网关进程打开；先停止旧进程 |
| drain后看不到新状态 | 检查来源绑定、查询端口及Entity消费，不删除队列绕过 |
| 重放显示旧版本被忽略 | 当前视图已有更高版本，是允许的状态去重 |
| 订阅缓冲超限断开 | 客户端太慢或订阅量过大，处理错误并重新初始化 |
| 收到心跳但无人机数据旧 | 连接活着与设备状态新鲜是两回事，检查expires_at |
