## 本次找到并处理的问题

1. 首次引导中断后缺少重建入口：增加专用维护流程和未完成状态保护。
2. 重建只改 ES 仍会受旧 Canal 位点及消费进度影响：明确保存快照边界并协调重置，拒绝活动消费组。
3. 消费组进度丢失后不能从快照之前的旧前缀开始：新增明确最早重放边界，必要历史缺失仍拒绝。
4. 临时测试输出进入发布清单：排除并增加检查；真实凭证、数据目录、Git 元数据不发布。
5. 演示把服务就绪误当实体状态新鲜：增加有界的快照等待，保留 Task 新鲜度校验。失败与复验都记录。
6. 旧 CI 没有 ES 环境：明确启动测试需要的依赖，不在该集成步骤误启动未初始化的 Canal。

## 保留的边界

这是本机模拟部署：RPC/ES 使用回环地址，机器随机凭证不是用户密码体系；没有生产 TLS/密钥托管、Kafka ACL 和多副本容灾。部署到真实网络必须另行设计。

搜索提供最终一致性，不保证响应一定包含刚提交的任务；任务操作始终回到 Task。PIT 是搜索视图，不是 MySQL 事务快照。standard 分词器已使用，但没有中文分词插件和搜索相关性调优，也没有搜索吞吐上限结论。

维护是有停机窗口的重建，不是自动无损热切换。Kafka topic 被外部删除后同名重建、MySQL 实例替换等外部身份变化不在当前完整自动检测承诺内，发生后应按维护流程重建；保留边界之外的原始历史、硬件执行事实或 MySQL 丢失不能靠 ES 重建恢复。

随后已补充整个根工程的 Linux 普通 race，以及搜索模块连接真实 MySQL/Kafka/ES 的 race；搜索 19 个顶层测试全部通过、零跳过，见 [race 补充记录](2026-09-12-linux-race.md)。远端 GitHub 443 连接超时，GitHub Actions 尚未实际执行；本机结果与远端 CI 仍分别报告。
