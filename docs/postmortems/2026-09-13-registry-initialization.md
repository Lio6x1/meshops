# 扩大实体基数时，初始化先于持续写入成为瓶颈

## 现象与定位

本轮准备百万实体容量测试时，先测注册表生成、加载、数据库初始化和启动校验。没有把模拟器参数直接调大就宣称已经支持百万实体。

Windows、i7-14650HX、Go 1.25.10、`GOMAXPROCS=2` 下，原有 JSON 清单仍经过 yaml.v3 解码。[修改前 CPU top](../../verification/2026-09-13-accounts-scale/initialization/manifest-before-top.txt)显示 `yaml.v3.(*decoder).mapping` 累计占样本 80.94%；源码对同一个映射中的键两两比较以拒绝重复，来源的 entities 映射扩大后开销明显。

真实独立 MySQL 中，一万实体 Seed 约 65.194 秒、40,004 条业务 SQL，CheckBindings 约 31.190 秒、20,002 条。每个绑定和实体分别查询、插入，使数据库往返次数随实体数增长。这里测的是初始化，不是上报吞吐。

## 修改与验证

生成的大清单采用 `.json`，加载时先用流式 JSON token 和哈希集合检查重复键，再严格解码到固定结构，拒绝未知字段、多文档和大小写别名。普通 YAML 保留，包括 `{key: value}` 流式语法；首次修改曾仅按首字符识别 JSON，独立审查发现兼容性问题，已加失败回归后修复为按 `.json` 扩展名选择。

同机[修改后基准](../../verification/2026-09-13-accounts-scale/initialization/manifest-after.txt)记录十万实体生成及加载 388,966,000 ns/op，累计分配 192,363,432 B/op，约 0.389 秒、192 MB。此次归档未提供修改前同一基准的原始输出，因此不把此前叙述的 2.739 秒/204 MB 当作已由本证据包复核的前后对比。B/op 是累计分配量，不是峰值 RSS，也不能据此宣称百万实体仅占这个内存。

数据库注册改为最多 500 行一批的预查和插入，仍共用一个事务。每批按确定顺序加锁、核对 JSON 和事实行，凭据、来源、代次、类型、执行器及任务目录冲突仍然拒绝。扩容仍只允许追加，出现跨批冲突会整体回滚。JSON 按批生成，避免提前持有全体实体的 JSON 副本。

| 实体数 | 操作 | 修改前 | 修改后 | SQL 数量前→后 |
| --- | --- | ---: | ---: | ---: |
| 1,000 | Seed | 7.861 s | 0.480 s | 4,004→12 |
| 1,000 | CheckBindings | 3.729 s | 0.040 s | 2,002→6 |
| 10,000 | Seed | 65.194 s | 1.926 s | 40,004→84 |
| 10,000 | CheckBindings | 31.190 s | 0.465 s | 20,002→42 |

这些是小规模实测，不按比例外推成百万实体吞吐保证。来源 JSON 仍是完整文档；注册仍持有完整事务，锁、undo 和各进程注册表内存都会随基数增长，必须继续观察真实容量测试。

## 供压路径也需要测量

实体基数、合计事件速率和连接数是不同维度。[七次容量归档](../../verification/2026-09-13-accounts-scale/capacity/README.md)中，第2次一万实体运行请求 2000 事件/秒，但生成 60,000 个事件花了 91.058 秒，实际只有 658.923 事件/秒，正确结果是 under_offered。累计接收数齐全也不能包装成目标速率通过。

检查发现负载发生器原先每条事件都读取并解析 fixture。在实际保留 run 目录的只读挂载及符号链接路径下，这个成本远高于直接访问镜像路径。现在每来源缓存一次只读模板，每事件创建独立映射并更新身份、版本、时间和事件 ID，仍经过 Normalize。

[生成器微基准](../../verification/2026-09-13-accounts-scale/generator/summary.json)使用 Linux、2 CPU、512 MiB、无网络、`GOMAXPROCS=2`，每次一秒、各三次。操作包含生成及 Normalize：

| 路径 | 每事件读盘/解析中位数 | 缓存模板中位数 |
| --- | ---: | ---: |
| 镜像 `/app/testdata/sources` | 26.006 µs/op | 16.065 µs/op |
| 保留 run 的 `/work/testdata/sources`，符号链接目标仍在镜像内 | 743.360 µs/op | 14.466 µs/op |

实际挂载路径约 51.4 倍的微基准差距支持供压路径的定位，不表示端到端吞吐提高同样倍数；必须重新运行真实负载。六类格式、模板不变性和每来源只读一次的测试分别保留，优化没有绕过校验。

## 已到达的一万与十万边界

第3次运行在一万不同实体下执行 500/2000/5000 事件每秒、每档 30 秒。前两档分别接收 15,000/15,000、60,000/60,000，errors/drops 为 0，最终两个消费组 lag 为 0，阶段通过；含排空接收速率分别为 499.841、1971.133 事件/秒。5000 档虽然实际生成约 4999.906 事件/秒，却只接收 120,220/150,000，生成队列丢弃 **29,780**，含排空耗时 51.748 秒，抽样生成→观测 p99 达 22,041.239 ms，故同次运行整体失败。ACK 错误为 0、末尾 lag 为 0 不能抵消丢弃。

第4次十万实体运行完成全部 100,000 份保留快照核验，并通过 500 事件/秒阶段。但预热含排空耗时 52.462 秒，来源过期阈值为 30 秒，核验时 **100,000 份快照全部过期**。这个通过结果证明身份/版本保留完整及所测负载，不保证十万实体同时新鲜，也没有十万实体 2000/5000 档的证据。详细指标、资源上限和全七次失败记录均在容量索引中。

## 百万初始化失败继续暴露语句边界

第5次百万运行没有进入预热：`database_seed` 返回 invalid connection，MySQL 多次出现 MY-014084 redo 空间无法回收、log_checkpointer 落后。[诊断转录](../../verification/2026-09-13-accounts-scale/capacity/redo-diagnosis.json)记录 redo 容量只有 **100 MiB**，buffer pool 256 MiB，max_allowed_packet 64 MiB。失败事务的绑定计数为 0，不能把提交前处理过的行数当成成功初始化。

把十份 Source JSON 单独插入再回滚时，31,801,970 字节 JSON 的服务端区间为 0.8741 秒，含 docker exec、传输、查询和回滚的端到端区间为 2.296 秒；单独插入成功。这支持检查完整事务中的 redo/checkpoint 压力，却没有排除 JSON 和 I/O 在持续写入下的成本，也没有证明完整百万初始化可行。

第6次仍初始化失败；其归档摘要未记录实际 redo 值，不补猜配置。第7次明确记录 **redo 1 GiB**，仍保持 MySQL 1 GiB 内存、2 CPU 上限，却再次失败。新增错误元数据定位到实体批次后的十条 Source 记录：`start=1000000 rows=10 parameter_bytes=31802820 elapsed=5.063214548s`。这一次 INSERT 的 binding key + JSON 参数共约 **31.8 MB**；它与诊断中仅 JSON 的字节口径不同。扩大 redo 没有单独解决问题，单条大语句在约 5 秒处失败值得继续验证；仅有底层错误类型不能确定唯一根因。

当前代码在原有 500 行预查边界之外，以 **4 MiB 软参数字节预算**拆分 INSERT。超预算单行独立发送，不裁剪来源 JSON；所有 INSERT 仍在同一个事务中，完整性冲突或失败会回滚，不能拆事务换取表面速度。该改动限制单次语句尺寸，不能消除完整事务的锁、undo/redo 或各进程注册表内存成本。

加入字节预算后的 fresh 百万复测正在运行，**当前没有通过结论**。后续第8次 run ID、完整预热及负载结果统一填入[容量记录的第8次补录区](../../verification/2026-09-13-accounts-scale/capacity/README.md#run-08)，不能用正在增长的进度代替完成结果。

## 防止再次误判

`TestBindingScaleRoundTrips` 检查真实数据库 SQL 次数预算，跨批冲突测试检查回滚和只追加约束；`BenchmarkScaleManifest` 可复测解析路径。容量测试把实体数和每秒事件数分开设置，并记录初始化失败、完整预热、消费积压、进程和容器资源。

独立审查还发现：压测原先只记录 ProjectorLag/HistoryLag，却没有将非零积压作为失败条件。现已对两个消费组进行有限排空，将等待计入吞吐；未完成消费、供压不足和超时都不能显示 passed。具体运行方式见[容量测试](../operations/scale-benchmark.md)。

## 新环境复测结果

第8次独立百万运行中，4 MiB 参数软预算后的 Seed 约 199 秒完成，服务启动成功；百万首次上报全部持久确认。但预热未限速，30 秒消费排空仍剩投影 472332 条、历史 326211 条，最终失败，未核验全量快照或运行后续 500/s。初始化改进与消费吞吐边界分别成立，不能以接收成功替代端到端通过。详见[第8次记录](../../verification/2026-09-13-accounts-scale/capacity/README.md#run-08)。
