# 六类实体数量扩展：既有环境注册升级

## 现象与原因

从每类一个实体改为每类五个后，第一次 Docker Up 在初始化阶段报告 `binding differs: source:demo_tenant:personnel_sim`，业务服务保持停止。原因是 `course_bindings` 保存了来源的完整原始 ID 映射，普通 seed 会比较全部字段；单纯改 YAML 不能修改既有注册事实。该保护防止凭证或实体归属被无意替换。

## 解决

新增显式维护入口 `seed --allow-entity-expansion`，Docker 初始化在停止业务服务后使用它。事务内只允许来源增加新 raw ID 映射，原映射、来源其它字段、实体归属、任务能力、代次及凭证哈希都必须保持一致。检查当前租户原注册记录，拒绝移除；任一冲突回滚整个事务。普通 seed 和启动绑定检查维持严格语义。未清空数据库、队列、搜索索引或凭证。

真实旧演示环境第二次 Up 已完成增量初始化。另有 `TestDemoEntityExpansionIsAdditiveAndAtomic` 使用随机隔离数据库，验证扩充、幂等、凭证冲突回滚和旧任务/Outbox保留；实际测试结果见本次验收记录。

## 验收脚本中的错误

第一次 30 实体 HTTP 验收已读到全部快照，但读取任务时错误地假定顶层包含 `status`，触发 KeyError。接口实际返回 `task.status`，并使用 `TASK_STATUS_SUCCEEDED` 枚举值。已修正脚本并重新执行；失败尝试保留在本机归档，不作为任务能力通过的证据。

后续新增示例清单时应同时考虑首次安装和已有数据的升级。不要通过清库掩盖绑定校验冲突，也不要把前端显示数量误当作实际已应用数量。
